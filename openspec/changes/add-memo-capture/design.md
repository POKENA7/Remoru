## Context

リポジトリにアプリケーションコードは存在せず、この change がすべての土台を作る。動機と範囲は proposal.md を参照。

制約は3つ。(1) 判断材料を早く出すことが最優先であり、足場は必要最小限に留める。(2) 認証・通知・AI・デプロイは後続の change に属し、ここでは扱わない。(3) 先行実装（`remoru-implementation` ブランチ）は参照してよいが、設計・スキーマ・コードを流用しない。

## Goals / Non-Goals

**Goals:**

- `openspec/changes/add-memo-capture/specs/memo-capture/spec.md` の要件を満たす最小の構成を決める
- change 3 で認証を接続する際に、データ移行を発生させない
- 後続の change が足場を作り直さずに機能追加だけで進める状態にする

**Non-Goals:**

- 本番環境の構成・デプロイ手順（change 3）
- スケジューラや出題ロジックの設計（change 2）— この change はメモを保存するだけで、メモがどう使われるかの構造には踏み込まない
- 性能・スケールの考慮。単一利用者が手で投入する規模しか想定しない

## Decisions

### 技術構成は先行実装と同じものを採る

Next.js (App Router) + Cloudflare Workers (`@opennextjs/cloudflare`) + D1 + Drizzle ORM + Vitest。

この選択の理由は技術的優位性ではなく**学習対象を1つに絞ること**にある。今回の主目的は OpenSpec を用いた開発の習得であり、未経験のスタックを同時に導入すると、詰まったときに原因が手法側にあるのか基盤側にあるのかを切り分けられなくなる。先行実装で一度通した地形を使えば、失敗の原因は手法側に限定される。

*検討した代替案:* 別スタックの採用 — 学習対象が二重になり、直近の停滞を繰り返す危険がある。先行実装のコード流用 — 方針上禁止であり、また流用すると OpenSpec で仕様を起こす練習の機会そのものが失われる。

なお構成が同じであることと、コードを流用することは別である。スキーマもコードも本 change で新規に書く。

### `userId` 列を固定値で先に置く

`memos` テーブルに `userId` 列を最初から設け、認証導入までは単一の固定値で埋める。

認証は change 3 に属するが、その時点で列を追加するとデータ移行が必要になる。列だけ先に置けば、change 3 の作業は「固定値を認証済み利用者の識別子に差し替える配線」に縮小する。`docs/intent-statement.md` の「技術的にマルチユーザー対応で設計する」という前提とも整合する。

*検討した代替案:* change 3 でマイグレーションを行う — 手数が増えるうえ、この時点でのコストはほぼゼロなので採らない。認証を change 1 に含める — 判断材料が一切出ないまま作業量だけが増えるため、探索段階で明確に退けた。

### 投入と一覧を単一画面に置く

spec の「投入から一覧への即時反映」要件を満たすための構成上の帰結。投入ページと一覧ページを分けると画面遷移が発生し、この change が判断しようとしている「メモ投入のしやすさ」そのものを悪化させる。

### 保存は Route Handler 経由とする

`POST /api/memos`（投入）と `GET /api/memos`（一覧）を Route Handler として実装し、クライアントから呼ぶ。

*検討した代替案:* Server Actions — App Router では自然だが、change 3 で認証を境界に差し込む際、HTTP の境界が明示されている方が接続先が分かりやすい。また利用者にとって観測可能な振る舞いは変わらないため、後から Server Actions へ移しても spec の変更は生じない。

### 本文の長さ上限は 1000 文字（暫定）

spec に数値として記載したが、根拠のある値ではない。「日常のちょっとしたこと」に対しては十分過ぎる余裕を持たせた暫定値である。

実際に使ってみて変更する場合、これは spec に書かれた観測可能な振る舞いなので、コードだけを直すのではなく spec の変更として扱う。この往復自体が OpenSpec の練習になる。

### テストの対象を絞る

この change には複雑な純粋ロジックが存在しないため、テストは次の3点に限定する。(1) 投入時のバリデーション（空・空白のみ・上限超過）、(2) 一覧が保存時刻の新しい順で返ること、(3) 保存が成功したメモが一覧に含まれること。

DB を伴うテストはインメモリの SQLite に対して実行し、実際の D1 には依存させない。UI の網羅率は追わない。

## Risks / Trade-offs

**この change の作業量の大半が足場に費やされ、「小さいはずが重い」と感じる** → tasks を「足場」と「機能」に分け、足場が終わった時点で開発サーバーが起動することを確認できる区切りを置く。手応えが得られない時間を短くする。

**OpenNext + D1 のローカル開発は `wrangler` 依存で、素の `next dev` とは挙動が異なる** → 足場の段階で D1 バインディングを伴う起動を一度確認するタスクを先に置き、機能を書いた後で基盤の問題に気付く事態を避ける。

**上限 1000 文字が実使用に合わない可能性** → 実際に使って判断する。変更は spec 経由で行うため、値が動いても記録は残る。

**単一画面構成はメモが増えると破綻する** → この change では単一利用者の手動投入しか想定しない。破綻する規模に達したら、その時点で別の change として扱う。

## Migration Plan

この change ではデプロイを行わない。動作確認はローカルのみ。

ロールバックは git 上の revert で足り、外部に影響する状態は生じない。D1 のマイグレーションもローカルデータベースにのみ適用する。

## Open Questions

- **一覧の件数上限とページング** — この change では全件を返す。単一利用者が手で投入する規模では問題にならず、必要になってから決めても spec・構成・タスク分割のいずれも変わらない。
