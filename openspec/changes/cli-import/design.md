## Context

- 投稿の入口は Server Action の `saveMemo` であり、`<form action={...}>` から呼ばれる (`features/memo/actions.ts:42`)。認証は `verifySession()` で行う。
- 書き込みは Server Actions に寄せてあり、`app/api` は無い (`docs/nextjs-rework-plan.md:76`)。
- Clerk を知るのは `lib/session.ts` だけである。取り込みの経路はClerkを使わないので、`verifySession()` も `getCurrentUserId()` も通らない。トークンの検証を足しても、`lib/session.ts` の外に Clerk の接点は増やさない。
- ドメイン関数は `(db, userId, …)` を受け取る形であり、テストが偽のデータベースで回る (`features/memo/queries.ts:8`)。
- 一覧の行は、一覧・復習状態・タグの3つの取得を組み立てて作る (`app/(app)/_containers/memo-list/container.tsx:39`)。APIでも同じ3つを使える。`listMemos` (`features/memo/memos.ts:66`)、`getReviewStates` (`features/quiz/quiz-items.ts:183`)、`getTagsForMemos` (`features/tag/tags.ts:136`) である。詳細の答えは `getQuizItem` (`features/quiz/quiz-items.ts:133`) から取る。
- `tests/architecture/auth.arch.test.ts:237` が「`app/api` は無い」を検査している。コメントには「サイト外からの操作で必要になったら、そのときここを直す」とある。
- `app/**` は `lib/db` と `drizzle-orm` を import しない規則が決まっている (`enforce-layer-boundaries` proposal)。データベースの取り出しは `queries.ts` / `actions.ts` に閉じる。
- 設定のための画面は無い。通知の設定は、復習画面から開くシートである (`features/review/components/review-screen.tsx:59`)。
- アカウントのメニューは Clerk の `UserButton` が出す (`features/memo/components/memo-tab.tsx`)。`@clerk/nextjs` 7 系の `UserButton.Link` で、このメニューに任意の経路への項目を足せる。
- `wrangler.jsonc` に KV も Durable Objects も無い。データベースは D1 だけである。
- 公開サインアップであり、誰でもアカウントを作れる。メモを1件保存するたびに、問答の生成で Anthropic の API を1回呼ぶ。費用と濫用の抑え方は `docs/intent-statement.md` の未確定事項である。
- 同じ保存時刻のメモは、一覧で `id`（ランダムな UUID）の順に並ぶ (`features/memo/memos.ts` の `listMemos`)。
- CLIを実行する利用者とAIに、ブラウザのサインインのセッションは無い。
- 調査を行うAIは、Remoru のリポジトリの外（別のプロジェクトや任意のディレクトリ）で動いている。リポジトリの `.claude/skills/` に置いた skill は、そのリポジトリで動くセッションにしか読み込まれない。

## Decisions

### D1: 入口は取り込みAPIを1つだけ置く。データベースへ直接書かせない

CLIからデータベースへ直接書くと、持ち主の紐づけと本文の検証と問答生成の起動を迂回してしまう。入口はAPIを1つだけ置き、中では既存のドメイン関数 (`createMemo`、`listMemos`、`getMemo`、`startGeneration`) を呼ぶ。Server Actionはブラウザのセッションが要るため、CLIからは使えない。

*採らなかった案*: Server Actionをトークンでも呼べる形に広げる。公開されたPOSTの宛先の認証を二重に持つことになり、見通しが悪くなる。

### D2: 認証は取り込み専用のトークンにする。1人1個に限る

要求の `Authorization` ヘッダで受け取る。トークンの平文はデータベースに置かず、SHA-256のハッシュだけを置く。平文は発行時に一度だけ示す。トークンでできることは取り込みAPIの範囲に限り、他の利用者のデータには到達できない。

**有効なトークンは利用者ごとに1個だけにする。** `import_tokens` の `user_id` を一意にする。発行済みの利用者がもう一度発行すると、古いトークンを消してから新しいトークンを作る（再発行）。失効は行を消すことで行う。失効済みの行を残さないので、失効済みのトークンが一覧に溜まることも無い。

1個に限るのは、使う場面が「自分の端末で動くAI」に限られるためである。端末ごとに分けて失効する必要は、いまは無い。個数に上限の無い発行は、D6 の上限を回避する手段にもなる。名前の列は、見分ける対象が1個しか無いので持たない。

*採らなかった案*: 利用者ごとに5個まで持てるようにする。端末ごとの失効はできるが、一覧・名前・個数の上限の管理が増える。必要になったら、`user_id` の一意の制約を外して戻せる。

### D3: Route Handlerの復活はこの用途の例外とし、経路は薄く保つ

`app/api` は書き込みを Server Actions に寄せるために削除した経緯がある。今回は外部の実行者がブラウザのセッションを持てないため、エージェント取り込みの用途に限って例外とする。画面からの書き込みは Server Action のままにし、寄せない。

`app/api/*/route.ts` は受け取りと応答だけを担う。トークンの検証とデータベースの取り出しは `features/import/request-context.ts` に置く。`app/**` が `lib/db` と `drizzle-orm` を import しない規則を、新しい経路でも守るためである。`middleware.ts` の照合対象は `api` を既に含んでいる。

`tests/architecture/auth.arch.test.ts` の「Route Handler は残っていない」は、「`app/api` の各経路が自分でトークンを確かめている」に置き換える。経路の認証を資源側に置く原則は変えない。

### D4: 操作は4つに絞る。読み取りも最初から入れる

- `POST /api/memos`。本文の配列を受け付ける。単件の登録は要素1件の配列とし、操作を増やさない。一覧と同じ資源に置く。登録は資源に対する作成であり、別の動詞の経路 (`/api/import`) は作らない。
- `GET /api/memos`。新しい順に返す。`tag` と `limit` の指定を受け付ける。復習の状態も含める。
- `GET /api/memos/[id]`。本文とタグと問答と次回出題日を返す。
- `GET /api/tags`。名前の一覧を返す。絞り込みと付与の前提になる。

読み取りの3つは、登録だけなら無くても成り立つ。それでも登録と同時に入れる。登録したAIが結果を確かめる手段になり、登録の前に既存のメモとの重複を確かめる材料にもなるためである（利用者の判断）。

一覧と詳細の組み立ては、一覧のContainerと同じ3つの取得を使う。返すのは本文・タグ・問答・次回出題日・復習の状態とし、`userId` は含めない。`limit` は `listMemos` に任意の引数として足し、既存の呼び出しは変えない。

**一覧の応答には問を含める。** 画面の一覧が問を出さないのは、本文から作られたものを二度読ませないためである（`memo-capture`）。APIの読み手はAIであり、同じ画面を見ていないので、この規則を持ち込まない。画面の一覧は変えない。

`limit` は応答を絞るだけで、復習の状態とタグは利用者のメモ全体から1回で求める。画面の一覧と同じ形である。メモが増えたときは、ここが重くなる（Risks）。

### D5: 登録は件単位で結果を返す。順序は配列の順に保つ

配列の中の1件が検証に落ちても、他の件の登録を止めない。応答は件ごとに成功と理由を返す。認証に失敗したときだけ全体を401で拒む。1回の上限は20件とし、超えた要求は受け付けない。

**保存時刻は「受け付けた時刻 + 配列の中の位置（ミリ秒）」にする。** 同じ時刻で保存すると、一覧での順序が `id` の順、つまりランダムになる（レビューで10件の並びが崩れることを再現した）。1件ずつ順に登録したときと同じ並びにするため、配列の後ろの件ほど新しくする。ずれは最大で19ミリ秒であり、復習の予定の日付には影響しない。

一括で登録した件は、同じ日に復習の対象になる。これは受け入れる（利用者の判断）。

*採らなかった案*: 1件でも落ちたら全体を取り消す。成功した件を1件の失敗のために捨てることになり、再送の手間が増える。

### D6: 費用の上限は、利用者ごとの1日の登録件数で数える

費用が増えるのは、メモ1件ごとに起きる問答の生成である。要求の回数で数えると、1回に20件を送れるため、件数が回数の20倍まで膨らむ。そのため、数える単位は要求ではなく件数にする。数える相手はトークンではなく利用者にする。

- 上限は**利用者ごとに1日100件**とする（暫定。実使用を見て見直す）。1回の上限20件（D5）はそのまま残す。
- 1日の区切りは UTC の日付とする。これは費用の歯止めであり、利用者に見せる日付ではない。利用者の地域の日付に合わせる必要は無い。
- `import_daily_usage` の表に、利用者と日付（エポックミリ秒を 86,400,000 で割った値）ごとに件数を持つ。要求を受け付けた時点で、送られた件数を1文の upsert で確保する。確保した結果が上限を超えるなら、確保を行わず、1件も保存せずに429を返す。
- 確保は検証の前に行う。検証で落ちた件も、確保した件数に数える。検証落ちのたびに枠を返す処理を足すより単純であり、上限に対して十分に小さい。
- 429 の応答には、翌日（UTC）までの秒数を `retry-after` に入れ、その日の残りの件数を本文に含める。
- 読み取りの要求は数えない（Risks）。

`wrangler.jsonc` に KV も Durable Objects も無いため、数え上げは D1 の表で行う。1文の upsert なので、同時の要求があっても件数は正しい。

*採らなかった案*: トークンごとに1分60回の要求の制限をかける（前の設計）。レビューで、1分あたり1,200件まで作れ、トークンの個数にも上限が無いことを確かめた。費用の歯止めになっていなかった。

### D7: CLIは `cli/` に独立したパッケージとして置く。どこからでも呼べるようにする

パッケージの公開は行わない。`cli/` は独自の `package.json` と `tsconfig.json` を持ち、`cron-worker/` と同じ扱いにする。`check:types` と `check:test` の対象に加える。トークンの置き場は利用者の設定ディレクトリ (`~/.config/remoru/`) とする。CLIにメモの分け方の知識は持たせない。運ぶだけにし、分け方はSKILL、検証はサーバが担う。

CLI は絶対パス（`node <リポジトリ>/cli/remoru.ts`）で呼ぶ。作業中のディレクトリに依存するのは `-f` に渡すファイルの位置だけにする。PATH に登録する方法（`npm link`）は採らない。Node のバージョン管理ツールで PATH が変わると呼べなくなるためである。

`login` は、保存する前に `GET /api/tags` でトークンが使えるかを確かめる。401 が返ったら保存せず、終了コード1で止める。通信に失敗したときも保存しない。貼り付け間違いのトークンを保存すると、次に登録するときまで誤りに気づけないためである。

### D8: 登録のコマンドは `memo add` に畳む

`memo add "本文"` が1件の登録、`memo add -f ファイル` が複数件の登録、`--dry-run` が送信せず候補を示す動きになる。別動詞の `import` は作らない。ファイルは空行で区切られた各ブロックを1メモとみなす。区切り方は機械的に決め、意味の判断はSKILLを読むAIに任せる。21件以上あるファイルは20件ずつに分けて送る (D5 の上限)。`--dry-run` は分割の結果だけを示し、サーバへは送らない。読み取り系には `--json` を付けられ、人は表として、AIは構造化された形として読む。

429 で1日の上限に当たったときは、送れた件と送れなかった件を分けて示し、残りの件数と再開できる時刻を出す。

### D9: SKILLは利用者単位の置き場に配置する

SKILL は、Remoru のリポジトリの外で調査しているAIに読まれなければ意味が無い。リポジトリの `.claude/skills/` に置くと、読み込まれるのは Remoru を開発しているセッションだけになる（前の設計の欠陥）。

- 元の文書は `cli/skill/SKILL.md` に置く。CLI の呼び出しは `{{REMORU_CLI}}` のような置き換え用の文字列で書く。
- `remoru skill install` が、置き換え用の文字列を CLI の絶対パスに置き換えて、`~/.claude/skills/remoru/SKILL.md` に書く。書き込み先は `--dir` で変えられる。既にあるファイルは上書きする（CLI の更新に合わせて入れ直せるようにする）。
- `allowed-tools` は、その絶対パスでの `node` の呼び出しだけに絞る。`Bash(node:*)` のように広くしない。
- リポジトリの `.claude/skills/remoru/` は置かない。残すと、Remoru の開発中のセッションで SKILL が起動し、本番にメモを登録するおそれがある。

内容は前の設計と同じにする。起動条件 (覚えたいと言われたら読む)、分け方の規則 (1メモ1事実、短く、上限1000字)、手順 (`--dry-run` での候補表示と利用者の確認を経て確定) を書く。「リポジトリのルートで実行する」の記述は消す。

### D10: トークンの画面は `/settings/api` の経路に置き、アカウントのメニューから開く

- `app/(app)/settings/api/page.tsx` に置く。読み取りはその経路の Server Component が `features/import/queries.ts` を通して行う。
- 入口は `UserButton.Link` で足す、アカウントのメニューの「API トークン」だけにする。メモ画面の上部のボタンは置かない。
- メモの一覧の描画では、トークンを読まない。

前の設計は、メモ画面の上部にボタンを置き、一覧を描画するたびにトークンを読んでシートへ渡していた。開く人がほとんどいない画面のために、全員の初期表示に取得を1つ足していた。進行中の初期表示の改善（`docs/nextjs-rework-plan.md`）とは逆を向いている。また、CLI を持たない利用者にとっては、押しても使えないボタンが常に見えていた。

画面が示すのは、トークンが有るか無いかと発行日である。操作は「発行」「再発行」「失効」の3つにする。再発行と失効は、使っている CLI が動かなくなるので、確認を1回挟む。発行した平文は、その画面に一度だけ示す。経路を離れると読めなくなる。

navigation spec が固有の経路を求めているのは4つの画面であり、それ以外の経路を禁じてはいない。この経路は下部のタブに加えず、タブは3つのままにする (`docs/design-decisions.md`)。戻り道は下部のタブである。

*採らなかった案*: Clerk の `UserButton.UserProfilePage` で、Clerk のモーダルの中に画面を置く。中身がクライアントで描画されるため、読み取りを Server Component で行う規則と合わない。

## Risks / Trade-offs

- トークンが漏れる。失効の手段を用意し、できる範囲を取り込みAPIに限り、平文を保存しないことで被害を抑える。漏れたトークンで作れるメモは、1日100件までである。
- 公開サインアップのため、どの利用者も1日100件まで生成を起こせる。費用の上限は「利用者の数 × 100件」で決まる。利用者の数そのものは抑えていない。これは画面からの投稿でも同じであり、`docs/intent-statement.md` の未確定事項として残る。
- 読み取りの要求は数えていない。漏れたトークンで読み取りを繰り返されると、Workers と D1 の読み取りの費用が増える。生成に比べて単価が小さいので、いまは数えない。
- **20件の生成が同時に走る**。1回の登録で、20件分の生成が1つの `waitUntil` の中で並行して起きる。Anthropic の API の同時実行の制限や、`waitUntil` の時間の制限で一部が失敗すると、そのメモは問答が無いまま残り、手で書くことになる。実際の API キーで測るまでは分からない（tasks 7.9）。失敗が出るなら、生成を順に起こすか件数を減らす。
- 一括で登録した件は、同じ日にまとめて復習の対象になる。受け入れる（D5）。
- `app/api` の復活が層の規則を緩める。経路を薄く保ち、トークンの検証とデータベースの取り出しを `features/import/` に置く。検査で `app/api` の各経路の認証を固定する。
- メモが増えると一覧の読み取りが重くなる。`limit` を付けても、復習の状態とタグは利用者のメモ全体から求める（画面の一覧と同じ）。重くなったら、1件ずつの取得に分ける。
