## Context

- 投稿の入口は Server Action の `saveMemo` であり、`<form action={...}>` から呼ばれる (`features/memo/actions.ts:42`)。認証は `verifySession()` で行う。
- 書き込みは Server Actions に寄せてあり、`app/api` は無い (`docs/nextjs-rework-plan.md:76`)。
- Clerk を知るのは `lib/session.ts` だけである。取り込みの経路はClerkを使わないので、`verifySession()` も `getCurrentUserId()` も通らない。トークンの検証を足しても、`lib/session.ts` の外に Clerk の接点は増やさない。
- ドメイン関数は `(db, userId, …)` を受け取る形であり、テストが偽のデータベースで回る (`features/memo/queries.ts:8`)。
- 一覧の行は、一覧・復習状態・タグの3つの取得を組み立てて作る (`app/(app)/_containers/memo-list/container.tsx:39`)。APIでも同じ3つを使える。`listMemos` (`features/memo/memos.ts:66`)、`getReviewStates` (`features/quiz/quiz-items.ts:183`)、`getTagsForMemos` (`features/tag/tags.ts:136`) である。詳細の答えは `getQuizItem` (`features/quiz/quiz-items.ts:133`) から取る。
- `tests/architecture/auth.arch.test.ts:237` が「`app/api` は無い」を検査している。コメントには「サイト外からの操作で必要になったら、そのときここを直す」とある。
- `app/**` は `lib/db` と `drizzle-orm` を import しない規則が決まっている (`enforce-layer-boundaries` proposal)。データベースの取り出しは `queries.ts` / `actions.ts` に閉じる。
- 通知の設定は専用の設定画面ではなく、復習画面から開くシートである (`features/review/components/review-screen.tsx:59`)。トークンの画面を置ける「設定画面」は無い。
- `wrangler.jsonc` に KV も Durable Objects も無い。データベースは D1 だけである。
- CLIを実行する利用者とAIに、ブラウザのサインインのセッションは無い。

## Decisions

### D1: 入口は取り込みAPIを1つだけ置く。データベースへ直接書かせない

CLIからデータベースへ直接書くと、持ち主の紐づけと本文の検証と問答生成の起動を迂回してしまう。入口はAPIを1つだけ置き、中では既存のドメイン関数 (`createMemo`、`listMemos`、`getMemo`、`startGeneration`) を呼ぶ。Server Actionはブラウザのセッションが要るため、CLIからは使えない。

*採らなかった案*: Server Actionをトークンでも呼べる形に広げる。公開されたPOSTの宛先の認証を二重に持つことになり、見通しが悪くなる。

### D2: 認証は取り込み専用のトークンにする。Clerkのセッションは使わない

利用者ごとに発行と失効ができるトークンを置く。要求の `Authorization` ヘッダで受け取る。トークンの平文はデータベースに置かず、SHA-256のハッシュだけを置く。平文は発行時に一度だけ示す。トークンでできることは取り込みAPIの範囲に限り、他の利用者のデータには到達できない。

### D3: Route Handlerの復活はこの用途の例外とし、経路は薄く保つ

`app/api` は書き込みを Server Actions に寄せるために削除した経緯がある。今回は外部の実行者がブラウザのセッションを持てないため、エージェント取り込みの用途に限って例外とする。画面からの書き込みは Server Action のままにし、寄せない。

`app/api/*/route.ts` は受け取りと応答だけを担う。トークンの検証とデータベースの取り出しは `features/import/request-context.ts` に置く。`app/**` が `lib/db` と `drizzle-orm` を import しない規則を、新しい経路でも守るためである。`middleware.ts` の照合対象は `api` を既に含んでいる。

`tests/architecture/auth.arch.test.ts` の「Route Handler は残っていない」は、「`app/api` の各経路が自分でトークンを確かめている」に置き換える。経路の認証を資源側に置く原則は変えない。

### D4: 操作は4つに絞る

- `POST /api/memos`。本文の配列を受け付ける。単件の登録は要素1件の配列とし、操作を増やさない。一覧と同じ資源に置く。登録は資源に対する作成であり、別の動詞の経路 (`/api/import`) は作らない。
- `GET /api/memos`。新しい順に返す。`tag` と `limit` の指定を受け付ける。復習の状態も含める。
- `GET /api/memos/[id]`。本文とタグと問答と次回出題日を返す。
- `GET /api/tags`。名前の一覧を返す。絞り込みと付与の前提になる。

一覧と詳細の組み立ては、一覧のContainerと同じ3つの取得を使う。返すのは本文・タグ・問答・次回出題日・復習の状態とし、`userId` は含めない。`limit` は `listMemos` に任意の引数として足し、既存の呼び出しは変えない。

**一覧の応答には問を含める。** 画面の一覧が問を出さないのは、本文から作られたものを二度読ませないためである（`memo-capture`）。APIの読み手はAIであり、同じ画面を見ていないので、この規則を持ち込まない。**画面の一覧は変えない。**

`limit` は応答を絞るだけで、復習の状態とタグは利用者のメモ全体から1回で求める。画面の一覧と同じ形である。メモが増えたときは、ここが重くなる（design Risks）。

### D5: 登録は件単位で結果を返す。認証の失敗だけ全体で拒む

配列の中の1件が検証に落ちても、他の件の登録を止めない。応答は件ごとに成功と理由を返す。認証に失敗したときだけ全体を401で拒む。1回の上限は20件とし、超えた要求は受け付けない。

*採らなかった案*: 1件でも落ちたら全体を取り消す。成功した件を1件の失敗のために捨てることになり、再送の手間が増える。

### D6: 速度の制限はデータベースの数でかける

`wrangler.jsonc` に KV も Durable Objects も無いため、メモリ上の数え上げは分離されたインスタンス間で共有されない。`import_rate_limits` の表に行を置き、トークンと1分の区切りごとに数を数える。1分あたり60回を超えた要求には429を返す。

数え上げ自体は1文の upsert で行うので、同じ1分の中では正しい。厳密でないのは区切りの方である。1分の境目をまたぐ短い間に、2倍まで通ることがある。守るのは濫用による費用の増大であり、攻撃の遮断ではないため、この精度で足りる。

**数えるのは登録の要求だけにする**（`POST /api/memos`）。費用が増えるのは登録であり、読み取りのたびに書き込みを1回増やす理由が無い。値は暫定とし、実使用を見て見直す。

### D7: CLIは `cli/` に独立したパッケージとして置く。配布はしない

初回はリポジトリからの直接実行だけに対応し、パッケージ公開は行わない。`cli/` は独自の `package.json` と `tsconfig.json` を持ち、`cron-worker/` と同じ扱いにする。`check:types` と `check:test` の対象に加える。トークンの置き場は利用者の設定ディレクトリ (`~/.config/remoru/`) とする。CLIにメモの分け方の知識は持たせない。運ぶだけにし、分け方はSKILL、検証はサーバが担う。

### D8: 登録のコマンドは `memo add` に畳む

`memo add "本文"` が1件の登録、`memo add -f ファイル` が複数件の登録、`--dry-run` が送信せず候補を示す動きになる。別動詞の `import` は作らない。ファイルは空行で区切られた各ブロックを1メモとみなす。区切り方は機械的に決め、意味の判断はSKILLを読むAIに任せる。21件以上あるファイルは20件ずつに分けて送る (D5 の上限)。`--dry-run` は分割の結果だけを示し、サーバへは送らない。読み取り系には `--json` を付けられ、人は表として、AIは構造化された形として読む。

### D9: SKILLの文書は `.claude/skills/remoru/SKILL.md` に置く

既存の skill は `.claude/skills/<名前>/SKILL.md` にあり、同じ置き場にする。起動条件 (覚えたいと言われたら読む)、分け方の規則 (1メモ1事実、短く、上限1000字)、手順 (`--dry-run` での候補表示と利用者の確認を経て確定) を書く。配布の仕組みは作らない。実行環境への手動の配置から始める。

### D10: トークンの画面はメモ画面の上部から開くシートにする

専用の設定画面は無く、通知の設定は復習画面から開く。同じく経路を増やさず、メモ画面の上部 (`UserButton` の並び) に入口を足して、シートで発行と失効を示す。タブは3つのままにする (`docs/design-decisions.md`)。

外枠は**共通の `Sheet`** を使う。閉じる手段（外側・引く・ボタン・Escape）と焦点の復帰を1箇所に持つためである (`sheet`)。自前の外枠を書くと、閉じ方を足したときに片方だけ直す形に戻る。

発行した平文はシートに一度だけ示す。閉じると読めなくなる。

## Risks / Trade-offs

- **トークンが漏れる**。失効の手段を用意し、できる範囲を取り込みAPIに限り、平文を保存しないことで被害を抑える。
- **公開後の濫用が課金につながる**。費用の懸念は `docs/intent-statement.md` の未確定事項にある。速度の制限と1回の件数上限で抑え、しきい値は運用で見直す。
- **`app/api` の復活が層の規則を緩める**。経路を薄く保ち、トークンの検証とデータベースの取り出しを `features/import/` に置く。検査で `app/api` の各経路の認証を固定する。
- **メモが増えると一覧の読み取りが重くなる**。`limit` を付けても、復習の状態とタグは利用者のメモ全体から求める（画面の一覧と同じ）。重くなったら、1件ずつの取得に分ける。

## Open Questions

- 速度の制限値 (1分60回) と1回の上限 (20件) は暫定である。実使用を見て見直す。
- この change はスキーマ、API、画面、CLI、SKILL を含み大きい。`agent-import-api` (トークン、API、画面) と `remoru-cli` (CLI、SKILL) に分ける案があった。**今回は1つで実装した。** 分けるなら、スキーマの変更を API 側に閉じたまま、CLI を後から足せる。
