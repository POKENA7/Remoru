## Context

動機は proposal.md を参照。画面設計と配色は `docs/design-decisions.md` に確定済み。

change 1・2 で用意してある足場が2つある。**`memos.userId` 列が最初から存在し**、固定値 `SINGLE_USER_ID` が入っている。そして**ドメイン層の関数はすでに `userId` を引数で受け取る**（`createMemo` / `listMemos` / `deleteMemo` / `createQuizItem` / `getReviewStates` / `countUnwritten` / `getDueItems` / `gradeReview`）。したがってこの change の作業は、**呼び出し側で何を渡すかを差し替えること**に集約される。データ移行もドメイン層の書き換えも発生しない。

**制約1: このリポジトリは public。** この change で初めてシークレットを扱う。鍵をコミットすれば公開の時点で漏洩であり、あとから消しても取り消せない。

**制約2: 先行実装はここで止まった。** 実装は完成していたのに実キーを入れず、一度もデプロイせず放棄された。この change の価値は、コードを書くことではなく**デプロイまで到達すること**にある。

**制約3: 認証事業者は差し替えの可能性が低いが、境界は要る。** Clerk を選ぶが、アプリの大部分が Clerk の型に依存すると、後で困るのはドメイン層になる。

## Goals / Non-Goals

**Goals:**

- 本番の URL を開いてサインインし、自分のメモを操作できる状態にすること
- 他の利用者のデータに到達できないことを、検査で担保すること
- 鍵を1つもリポジトリに入れないこと
- デプロイの前にテストが走り、落ちたら出荷されないこと

**Non-Goals:**

- 認証事業者を差し替え可能にすること。Clerk に寄せる。ただし後述の1点だけ境界を引く
- プロフィール、表示名、アバターなどの利用者情報。サインインできれば足りる
- 権限や役割。利用者は自分のデータだけを扱う
- 複数端末間の同期の最適化。サーバーにあるので自然に揃う

## Decisions

### D1: 利用者の識別は1箇所に閉じる

セッションから利用者を取り出す関数を1つだけ用意し、API のルートはそれを呼ぶ。ドメイン層は Clerk を知らない。

```
getCurrentUserId() -> string | null     ← ここだけが Clerk を知る
```

Clerk の識別子をそのまま `memos.userId` に入れる。独自の利用者テーブルを作らない。**先行実装は `users` テーブルを作って Clerk の識別子と対応づけていたが、この change で必要になる情報は識別子だけである。** 通知の時刻やタイムゾーンが要る change 4 で、必要になった時点でテーブルを足せばよい。

*代替案*: いま `users` テーブルを作る。却下。この change で読み書きする列が1つも無い。

### D2: 識別子は要求から受け取らない

利用者の識別子を要求の本文・問い合わせ文字列・経路から受け取らない。常に `getCurrentUserId()` から得る。

これは spec の要件であり、**先行実装で実際に踏んだ形**でもある。先行実装の内部向けエンドポイントは認証middlewareから除外されたうえで、要求本文の `userId` を信じて処理していた。共有の秘密で守られてはいたが、値を渡せる構造そのものが危うい。

この change ではドメイン層の関数が `userId` を引数に取るため、**ルートが誤ってそこに要求由来の値を渡す**経路が実在する。規約では防げないので検査で防ぐ（D5）。

### D3: 未認証は middleware で止める

Next.js の middleware で、公開する経路（サインイン・サインアップ・静的資産）以外を認証必須にする。個々のルートで確認を書き忘れる余地を無くす。

**Clerk は `createRouteMatcher` を非推奨にしており**、「middleware のパス一致は Next.js のルーティングと乖離しうるため、保護されるべき資源に到達できる場合がある」と警告している。したがって **middleware を唯一の防御にしない**。各 API ルートが単独でセッションを確認し、未認証なら 401 を返す。middleware は画面のリダイレクトと二重化のために置く。この二重化は D5 の検査で担保する。

未認証の API は画面へリダイレクトせず 401 を返す。リダイレクトすると `fetch` は HTML を受け取り、クライアントは「認証が必要」ではなく一般的な失敗として扱ってしまう。

**除外リストに `/api/` 配下を安易に入れないこと。** 先行実装は内部向けエンドポイントのために `/api/internal/(.*)` を公開扱いにしていた。この change では除外は認証画面と静的資産のみとする。

### D4: 鍵はリポジトリに入れない

- ローカル: `.env.local`（`.gitignore` の `.env.*` で除外済み）
- 本番: `wrangler secret put` で Cloudflare のシークレットストアへ
- `.env.example` にはプレースホルダだけを置く

`clerk init` が `.env.local` に書くため、当初想定していた `.dev.vars` ではなく
そちらを使う。**この2つは効く場面が違う。** `.env.local` は `next dev` が読み、
`.dev.vars` は Workers ランタイム（`npm run preview`）が読む。鍵の置き場所を
2つに増やすと転記漏れが事故になるため、ローカルは `.env.local` 一本とし、
Workers ランタイム上での確認は本番デプロイ（タスク6.3〜6.5）に集約する。

公開鍵（`NEXT_PUBLIC_*`）はクライアントに出るものなので `wrangler.jsonc` の `vars` に置いてよい。秘密鍵は置かない。

### D5: 分離はテストで担保する

利用者の分離は「気をつける」で守れない。次の3点を検査する。

| 検査 | 何を防ぐか |
|---|---|
| 別利用者のデータに到達できないこと（各 capability） | 取得・更新・削除の漏れ |
| ルートが要求由来の値を `userId` に渡していないこと | D2 の違反 |
| middleware の除外リストが認証画面と静的資産だけであること | D3 の違反 |

後ろ2つはソースを検査する形になる。スケジューラの import 境界テスト（change 2 の D2）と同じ考え方で、**レビュアーが居ないので規約ではなく検査で守る**。

### D6: デプロイはテストを通さないと進まない

`npm run deploy` がテスト・型チェック・ビルドを順に実行し、どれかが落ちたら出荷しない。

先行実装の deploy はビルドと出荷だけで、**赤いまま出荷できた**。同じ形にしない。

### D7: PWA は manifest まで

manifest とアイコンを置き、ホーム画面に追加できるようにする。**Service Worker はこの change では入れない。** Service Worker はプッシュ通知のためのものであり、使う change 4 と同時に入れる。いま入れると、何もしない Service Worker がキャッシュの挙動だけ変えて、原因の分からない不具合の温床になる。

## Risks / Trade-offs

- **[公開サインアップにしたことで費用と濫用の余地ができた]** 誰でも登録でき、change 5 で AI 生成が入ると他人の利用がそのまま課金につながる → この change では対処しない。`docs/intent-statement.md` に未確定事項として記録済み。change 5 の設計時に、呼び出し回数の上限などを検討する
- **[Clerk への依存]** 認証まわりは Clerk の型と手順に寄る。事業者を変えるなら書き直しになる → D1 の1関数だけが境界であり、ドメイン層は影響を受けない。UI とルートは書き直す前提で受け入れる
- **[既存のローカルデータが孤児になる]** `SINGLE_USER_ID` のデータは持ち主が居なくなる → 開発中のテストデータのみなので破棄する。本番は空から始まる
- **[デプロイの手順は一度しか通らない]** 本番の D1 作成やシークレット登録は初回だけの作業で、手順の誤りは次回まで気づけない → 手順を文書に残す。ただし文書は実行されないので、**実際に本番の URL でサインインして操作できることを確認するまで完了としない**
- **[Workers ランタイム上の認証を、本番で初めて試すことになる]** ローカルは `next dev` のみで確認し、`npm run preview` を飛ばす判断をした。認証が Workers ランタイムで動くかどうかは本番デプロイまで分からない → これは先行実装が詰まった構図（実キーと実環境を最後まで試さない）に一部近い。緩和は、タスク6.5 を「本番の URL で実際に一周する」まで完了としないこと。ここで落ちたら `npm run preview` に戻って切り分ける
- **[workers.dev のサブドメインは変えにくい]** 後から独自ドメインに移すと URL が変わり、ホーム画面に置いたアイコンは古い URL を指したままになる → 独自ドメインが要るのは公開範囲を広げるときで、そのときは移行の手間を受け入れる

## Migration Plan

1. Clerk のアプリケーションを作成し、鍵を取得する
2. ローカルの `.dev.vars` に入れて、サインインが通ることを確認する
3. `SINGLE_USER_ID` の参照をセッション由来の識別子に差し替える
4. 分離の検査を追加する
5. 本番の D1 を作成し、マイグレーションを適用する
6. シークレットを登録し、デプロイする
7. **本番の URL でサインインし、メモの投入から復習までを実際に通す**

**ロールバック**: 認証の導入前に戻すには、middleware を外し `getCurrentUserId()` を固定値に戻す。データはそのまま残るが持ち主が変わるため、開発データは破棄する前提。本番にデータが入ったあとのロールバックは想定しない。

## Open Questions

- 利用者が増えたときの費用の上限をどう設けるか → change 5 の設計時に、AI の呼び出し回数と合わせて検討する
- アカウントの削除（利用者が自分のデータごと消す）→ 必要になってから。いまは自分しか居ない
