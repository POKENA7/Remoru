## Context

動機は proposal.md の `## Why` を参照。ここでは設計を説明するのに必要な現状と制約だけを述べる。

**制約1: 棚卸の場で人間が判断できなければならない。** これが前例から得られた最も重要な制約である。旧 AI-DLC の仕組みは捕捉も出所追跡も admission gate も備えていたが、記録された学びが一般論だけで書かれていたため、「残しますか」に答えられなかった。判断できない記録は、増えるほど棚卸を形骸化させる。設計判断が競合したときは、判断可能性を優先する。

**制約2: 仕組みの不在が原因ではない。** 旧 AI-DLC には必要な部品が揃っていた。したがってこの change の価値は、部品を追加することではなく、**記録の書き方**と**出ていく経路**を定めることにある。

**制約3: 単独開発者。** 捕捉する人・承認する人・仕組みを維持する人が同一人物。手作業のステップは、それが1つでもあると回らなくなる可能性が高い。

**制約4: 稼働が断続的。** 趣味のプロジェクトであり、3週間触らないことがある。時間ベースの判定はこの前提と両立しない。

**利用可能な足場**: `CLAUDE.md` の `@import`（同リポジトリで実証済み）、git の commit trailer、OpenSpec の change アーカイブという既存の区切り。いずれも新規に作る必要がない。

## Goals / Non-Goals

**Goals:**

- 記録された学びが、**半年後の本人が判断できる**形になっていること。判断の材料は「規則」ではなく「出来事」である
- **学びが自然に出ていく**設計にすること。入口だけの仕組みは必ず膨らむ
- 文脈を圧迫しない程度に**量を抑える**こと。硬い予算ではなく、しきい値と棚卸で抑える
- 段階1を**ツールなしで**成立させること。スクリプトが必要な設計は、スクリプトが壊れた日に止まる
- この仕組み自体が正しいかを、**後から検証できる**ようにすること（メタ評価）

**Non-Goals:**

- 学びの**質**を測ること。引用数は「使われた」を測るのであって「役に立った」を測らない（`## Risks / Trade-offs` 参照）
- 厳格なバイト予算を課すこと。前例が捨てられた理由はサイズではなかったため、サイズを一次制約に据える根拠がない
- 学びの分類体系や検索性。この規模に索引は要らない
- 他のプロジェクトへの再利用可能な汎用フレームワーク化
- 自動的な捕捉（セッションログの解析など）。段階3の検討事項

## Decisions

### D1: 学びは「規則 + それを生んだ具体的な出来事」で書く

これが制約1への直接の回答であり、旧 AI-DLC の仕組みとの実質的な差分である。

```markdown
- **[L04] 配色の性質を主張する前に実測する**
  ダークモードを「暖色ベースにした」と報告したが、測ったら背景は色相257＝紫だった。
  意図ではなく、レンダリング結果の計算値で確かめる。
```

1行目が規則（走査用）、2行目が**出来事**、3行目が次にどうするか。棚卸のとき人間が読むのは2行目である。「ああ、あれか」と思い出せるかどうかが、残す/消すの判断を可能にする。

出来事には可能なら**代償**を含める（「2回踏んだ」「3回失敗した」）。代償は、その学びを残す価値の直接の根拠になる。

*代替案*: 規則だけを簡潔に書く（旧 AI-DLC の `## Corrections` 方式）。却下。短くはなるが、棚卸で判断できなくなる。実際にそうなった。行数を惜しんで判断可能性を失うのは、この設計で最も避けたい取引である。

### D2: 学びには強度の階層があり、多くは散文より検査として書いたほうが強い

強い順に: **実行可能な検査（テスト/lint/CI） > 生成時に必ず読まれる設定 > セッション開始時に読まれる文書 > どこかにある散文のメモ**。

`.learnings/active.md` は上から3番目でしかない。したがって「学びを記録する」ことは最終目的ではなく、**より強い層に押し上げられるまでの一時的な置き場**として設計する。これが後述の「昇格」の根拠であり、採用基準4（コードやテストに書けるなら、そちらに書く）の根拠でもある。

### D3: ライフサイクルは「捕捉 → 適用 → 評価 → 削除 または 昇格」

出口を2つ持つことが要点である。**使われなければ削除、よく使われれば昇格。どちらも active から出ていく。** 残るのは「たまに使うが、まだコードに落とせないもの」だけになる。

*代替案*: 出口を「削除」だけにする。却下。よく使われる学びほど削除されず永住するため、最も価値の高い項目がファイルを埋め尽くす。昇格がないと、成功した学びが仕組みを重くするという逆向きのインセンティブになる。

### D4: 件数しきい値（12件）は硬い壁ではなく、棚卸の起動条件である

active が12件を超えたら棚卸を行う。**13件目をブロックはしない。** 棚卸を済ませるまで学びを捨てさせる設計にすると、価値ある学びが入口で失われるうえ、捕捉のたびに棚卸が割り込んで捕捉自体が避けられるようになる。

12件という数値に理論的根拠はない。「一覧して目視で判断できる上限」という実務的な目安である。この数値が適切かは運用してから見直す（`## Open Questions`）。

*代替案*: しきい値なし＋定期的な棚卸し。却下。旧 AI-DLC がこれで、棚卸しは一度も行われなかった。件数による起動は、棚卸を「思い出したらやること」から「条件が揃ったらやること」に変える。
*代替案*: 硬い上限にして13件目をブロックする。却下。上記のとおり、捕捉を阻害する副作用のほうが大きい。

### D5: 採用基準は4つで、4つ全部を満たすものだけを記録する

1. **具体的な出来事がある**（一般論だけのものは記録しない。出来事を書けないなら、それは学びではなく意見である）
2. **次も確実に遭遇する**（一度きりの偶発ではない）
3. **再導出にコストがかかる**（エラーメッセージを見れば分かる、なら不要）
4. **コードやテストに書けない**（書けるなら、そちらに書く＝即昇格）

AND 条件であることが重要。OR や「おおむね満たす」にすると、ほぼすべての気づきが通過する。

基準1は制約1から導かれる新しい基準であり、**旧 AI-DLC に記録されている5件はいずれもこの基準で落ちる**。これは基準が機能している証拠であって、過去の記録を否定するものではない — 同じ内容を出来事付きで書き直せば通る。

#### 門が実際に機能した証拠: change 1 の選別実例

`add-memo-capture`（change 1）で得られた候補8件を上記の基準にかけた結果:

| 候補 | 判定 | 理由 |
|---|---|---|
| `rm` が対話モードにエイリアスされている | **採用 L01** | コマンドが2分間ハングして初めて気づいた。シェル設定はエラーからは読み取れない |
| `noclobber` が有効（`cat > file` が既存ファイルで失敗） | **採用 L02** | 今回2回踏んだ＝基準2を実測で充足 |
| headless Chrome の配色切替は CLI フラグでは効かない | **採用 L03** | 3回失敗した。フラグは静かに無視されるため、エラーからは分からない |
| 配色の性質を主張する前に実測する | **採用 L04** | 「暖色ベース」と報告して実際は色相257の紫だった。判断の癖でありコードに書けない |
| spec のシナリオをブラウザで一通り辿る | **採用 L05** | 単体テストが見逃す欠陥（古いエラー表示が残る）をこれで発見した |
| アクセント色を反転したら文字色も反転する | **昇格** | 基準4で落ちる＝コントラストの回帰テストとして書ける。change 1 で実際に 2.52:1 の基準割れを起こした |
| `rm` の対話モード（別の言い回し） | **却下** | L01 に統合。重複 |
| npm overrides の入れ子構文が効かない | **却下** | 遭遇頻度が低く（基準2×）、再導出も容易（基準3×） |

8件中、active に入ったのは5件。1件はより強い層へ、2件は消えた。この分布そのものが、基準が門として働いていることの証拠である。

### D6: ファイルは3つに分け、文脈に入るのは1つだけ

```
.learnings/
├── active.md      学びの置き場。CLAUDE.md から @import され毎セッション読まれる
├── index.json     ID・種別・捕捉元 change・引用数。文脈には読み込まない
└── archive.md     削除・昇格したもの。理由付き。文脈には一切読み込まない
```

分割の目的は整理ではなく**読む量の分離**である。メタデータ（引用数、捕捉元）や履歴（archive）は、記録する価値はあるが毎セッション読む価値はない。`active.md` に同居させると、判断に使う出来事の記述が埋もれる。

### D7: `CLAUDE.md` から `@.learnings/active.md` を @import する

1行の追加で毎セッション確実に読まれる。この方式は**同リポジトリで実証済み**である（AI-DLC が `@.claude/rules/aidlc.md` から推移的に7ファイルを読み込んでいた）。

*代替案*: フックで動的に注入する。却下。段階1をツールなしで成立させる Goal に反する。段階3で条件付き読み込みを検討する余地は残す。

### D8: 引用は commit trailer で記録する

学びを適用したコミットに1行足す。

```
fix: ダークモードの配色を暖色に寄せる

Learning: L05
```

集計は `git log --grep "Learning: L05" --oneline | wc -l`。

理由は3つ。**追加の手間がゼロ**（コミットは元々書く）、**git に永久に残る**（別ファイルのように消えたり同期がずれたりしない）、**grep できる**（集計にツールが要らない）。制約3への直接の回答である。

*代替案*: 専用の引用ログファイルに追記する。却下。コミットとは別の手作業が増え、書き忘れの機会が二重になる。

### D9: 評価の時計は「アーカイブされた change の数」であり、経過日数ではない

```
引用0件 かつ 3 change 経過  → 削除を提案
引用3件以上                 → 昇格を提案（テスト/lint/config へ）
それ以外                    → 継続
```

制約4への対応である。カレンダー時間で測ると、3週間触らなかっただけで、まだ一度も試される機会のなかった学びが削除される。change 数は**実際に作業した量**を測るので、「試される機会があったのに使われなかった」という削除の根拠と一致する。

削除は**提案までで、承認は人間**が行う。判断できるだけの材料（出来事）が D1 で保証されているので、この承認は形式的なものにならない。

*代替案*: 日数ベース（例: 30日）。却下。上記の理由。
*代替案*: 削除を全自動にする。却下。引用が自己申告である以上、書き忘れが即削除につながる。

### D10: メタ評価は「再捕捉の検知」で行う

削除した学びは `archive.md` に**理由付きで**残す。**同じ学びが後で再捕捉されたら、それは「削除規則が厳しすぎる」という信号**として扱う。

これがこの設計の中で唯一、仕組み自体を評価する仕掛けである。これがないと、削除規則（3 change）が正しいかを**永久に知ることができない**。archive.md は文脈に読み込まないので、この検証能力は文脈の消費なしに得られる。

### D11: 段階導入。この change のスコープは段階1のみ

最小構成で一度回してから足す。段階2（`review.mjs`、npm script、archive guidance）と段階3（`Stop` フック、条件付き読み込み）は proposal.md に「今回やらないこと」として記載済み。

段階1で棚卸が手作業で済むのは、件数が目視できる規模に留まるからである（D4）。

## Risks / Trade-offs

- **[判断可能性の担保は自己規律に依存する]** D1 の形式（出来事を書く）を守るかどうかを機械的に強制する手段が段階1にはない。急いでいるときに規則だけ書いてしまえば、旧 AI-DLC と同じ状態に戻る → 緩和は採用基準1を明文化し、`active.md` のヘッダに形式を書いておくこと。**完全な緩和ではない**。段階2で `review.mjs` に「出来事の行があるか」の検査を入れる余地がある。
- **[引用は自己申告である]** 学びを適用したのに trailer を書き忘れると、実際には生きている学びが「引用0件」と判定されて削除提案の対象になる → 緩和は D10 の archive + 再捕捉検知。削除された学びが再び必要になれば archive.md に同じ内容が再登場し、規則の誤りとして観測できる。**ただし再捕捉されるまでは誤削除に気づけない**。
- **[引用数は「使われた」であって「役に立った」ではない]** 質は測れていない → 部分的な緩和として、引用3件以上を削除ではなく**昇格**の契機にしている（D3/D9）。昇格先はテストや lint であり、そこで実際に効くかは検査が通るか否かで判定される。散文のままでは判定できない質が、より強い層に移した時点で判定可能になる。
- **[捕捉者と承認者が同一人物である]** 単独開発者なのでレビューに客観性がない。自分が書いた学びを自分で「有用だ」と判定する構造は、原理的に甘くなる → **他メンバーが入るまで構造的に解決できない**。既知の限界として記録する。
- **[出来事を書くぶん1件が長くなる]** 判断可能性と引き換えに、毎セッション読む量は増える。旧仕組みより1件あたりのコストは高い → これは意図した取引である。判断できない記録を大量に持つより、判断できる記録を少数持つほうがよい。量は件数しきい値と棚卸（D4/D9）で抑える。
- **[12件という数値に根拠がない]** 目視できる規模、という実務的な目安でしかない。厳しすぎれば棚卸が頻発し、緩すぎれば文脈を圧迫する → 段階1を回して、棚卸の起動回数と実際の負担感から見直す（`## Open Questions`）。

## Migration Plan

既存システムへの変更を伴わないため、移行らしい移行はない。

1. `.learnings/` を作成し、初期5件を投入する
2. `CLAUDE.md` に @import の1行を追加する
3. 次の change から commit trailer による引用を始める

**ロールバック**: `.learnings/` を削除し、`CLAUDE.md` の1行を戻す。それだけで完全に元に戻る。製品コードもスキーマも依存関係も触らないため、副作用は残らない。過去のコミットに残った `Learning:` trailer は無害な文字列として残る。

## Open Questions

以下は**今答えなくても approach・タスク分解のいずれも変わらない**ため、段階1を回して得られるデータで後から答える。

- 件数しきい値（12件）は妥当か → 棚卸の起動回数と、そのときの負担感で判断する
- 削除規則の閾値（3 change）は妥当か → D10 の再捕捉検知で観測する
- 昇格規則の閾値（引用3件）は妥当か → 昇格した学びが昇格先で実際に効いたかで判定する
- 段階2に進むべきか → 段階1の棚卸が実際に回るかを確認してから判断する
