## Context

動機は `proposal.md` の `## Why`、要件は `specs/` を参照。ここでは制約と選択だけを書く。

**制約1: メモの投入の速さは成功指標そのもの**（`docs/intent-statement.md`）。
生成に数秒かかるため、保存の応答をそれに引きずらせられない。

**制約2: いまの「未作成」は問答の不在で表している。** `quiz_items` に行が
無ければ未作成、というだけの判定なので、**「いま作っている最中」を表現できない**。

**制約3: 復習の段階は `review_schedules.quiz_item_id` に紐づいている。**
問答を消して作り直すと、外部キーの連鎖削除で段階も消える（`db/schema.ts`）。

**制約4: 本体は Cloudflare Workers 上で動く。** Node の常駐プロセスは無い。
リクエストが返ったあとに仕事を続ける手段は、ランタイムが用意するものに限られる。

**制約5: このリポジトリは公開サインアップ。** 生成は課金される。

## Goals / Non-Goals

**Goals:**

- 書いたら、何もしなくても復習に入ること
- 生成が失敗しても、アプリが以前より悪くならないこと
- 鍵が無い環境でも動くこと（ローカル開発、鍵の入れ替え中）

**Non-Goals:**

- 生成の品質を評価する仕組み。良し悪しは利用者が作り直しで判断する
- 1メモから複数の問答を作ること。1メモ1問答は `quiz-item` の既存要件
- 手動で問答を編集する画面。いまも無い。作り直しと、未作成からの手動作成で足りる
- 利用回数の上限（D8 を参照）

## Decisions

### D1: 生成は応答を返したあとに走らせる

メモの保存は生成を待たない。保存を確定して応答を返し、生成はランタイムが
用意する「応答後も続く実行」の枠（Workers の `waitUntil`）で行う。

*代替案*: 保存の要求の中で生成まで待つ。却下。投入が2〜4秒待たされる。
制約1に真正面から反する。

*代替案*: 生成専用の worker とキューを挟む。却下。いまの規模で運ぶものが
増えるだけで、失敗の扱いは変わらない。cron worker を別に立てたのは
「本体の要求とは無関係に定時で動く」必要があったからで、生成にはその必要が無い。

### D2: 「生成中」はメモ側の列で表す

`memos` に生成の状態を1列持つ。一覧の状態は次の順で決まる。

| 条件 | 表示 |
|---|---|
| 問答がある | 作成済み（次回出題日） |
| 問答が無く、状態が「生成中」 | 作成中 |
| それ以外 | 未作成（手動作成の導線） |

*代替案*: `quiz_items` に「未完成」の行を先に作る。却下。`quiz-item` の
既存要件が「問と答はいずれも必須。片方だけで保存しない」と定めており、
中身の無い行はこれに反する。

*代替案*: 生成の状態を別テーブルに持つ。却下。1メモに1つしか無い状態のために
一覧の読み取りへ結合が1つ増える。

### D3: 生成は Claude を使い、モデルは Haiku から始める

`claude-haiku-4-5-20251001` を使う。入力は1〜2文のメモ、出力は問と答の
2文字列で、抽出の難易度は高くない。速さと費用がそのまま利用体験に効く。

品質が足りなければモデル名を差し替える。**モデル名を置くのは1箇所に限る。**

*代替案*: Cloudflare Workers AI（外部の鍵が要らない）。却下。日本語の
短文からの問答の抽出は品質の差が出やすく、ここは本体機能である。

### D4: 出力は道具呼び出しで受け取る

問と答を引数に持つ道具を1つ定義し、モデルにそれを呼ばせる。自由文から
JSON を切り出す処理を持たなくて済み、形の検証が入口で済む。

**返ってきた値は文字列としてしか扱わない。** 長さの上限を超えるもの、
空のものは失敗として扱う。メモの本文はモデルへの入力に入るため、
**出力を指示として解釈する経路を作らない。**

*代替案*: 「JSON だけを返せ」と指示して解析する。却下。前置きが混ざる、
コードブロックで囲まれる、といった揺れの処理を自前で持つことになる。

### D5: 作り直しは行を置き換えず、中身を書き換える

問答の作り直しは `quiz_items` の行を削除して作り直すのではなく、
**同じ行の問と答を書き換える**。制約3のとおり、削除すると復習の段階まで
消える。spec の「作り直しても復習の進みは残る」はこの一点で決まる。

*代替案*: 削除して作り直し、段階を写し替える。却下。写し替えの間に
失敗すると段階が失われる。書き換えなら失敗しても元のまま残る。

### D6: 失敗は静かに未作成へ落とす

生成の失敗を利用者に警告として出さない。一覧では未作成として現れ、
手で書く導線が出る。`docs/design-decisions.md` の「責めない」トーンと同じ。

**ただし失敗は記録に残す。** 生成が常に失敗しているのに気づけない状態を作らない。

### D7: 鍵が無ければ生成を起こさない

`ANTHROPIC_API_KEY` が無い環境では、生成を試みず最初から未作成にする。
ローカル開発と、鍵を入れ替えている最中に、投入そのものが壊れないようにする。
change 4 で通知の鍵に対して同じ形（鍵が無ければ機能が現れないだけ）を取っている。

### D8: 利用回数の上限は入れない

利用者の明示的な判断。**公開サインアップなので、他人の利用がそのまま課金に
なる。** 上限は必要になってから入れる。

代わりに**気づく手段だけ**は置く。生成の実行と失敗をログに出し、金額の監視は
Anthropic 側のダッシュボードに委ねる。

### D9: 一覧は「作成中」が消えるまで数回だけ問い合わせる

生成は背景で走るので、保存直後の一覧は「作成中」で描かれる。完了は
自動では届かない。一覧に「作成中」が1件でもある間、**上限を決めて数回だけ**
取り直す。上限に達したら止め、次に開いたときに反映する。

*代替案*: 常時ポーリング。却下。生成が終わったあとも問い合わせ続ける。
*代替案*: 何もしない。却下。書いた直後に「作成中」のまま止まって見え、
生成が動いていないのと区別がつかない。

## Risks / Trade-offs

- **[応答後の実行が最後まで走る保証は無い]** ランタイムが打ち切れば生成は
  途中で終わる → 状態が「生成中」のまま残る。**一定時間を過ぎた「生成中」は
  未作成として扱う**ことで、永久に作成中のまま留まるメモを作らない
- **[費用が読めない]** D8 のとおり上限を入れない → 実行と失敗をログに出し、
  気づく手段は残す。これは緩和であって解決ではない
- **[メモ本文がモデルへの入力に入る]** 本文に指示めいた文字列を書けば出力を
  歪められる → 出力は問と答の2文字列としてしか使わず、長さを制限する。
  出力から処理を分岐させない（D4）
- **[生成の品質]** 短いメモからは良い問いが作れないことがある → 作り直しで
  対処する。品質を測る仕組みは Non-Goal
- **[モデルの応答が遅い]** 保存は待たないので投入体験には影響しないが、
  一覧の「作成中」が長く残る → D9 の上限に達したら止める

## Migration Plan

1. `memos` に生成の状態の列を足す（既存行は未作成として扱われる値で埋まる）
2. 生成の呼び出しを、純粋な部分（プロンプトの組み立て・応答の検証）と
   外部呼び出しに分ける
3. 保存後に生成を起こす。鍵が無ければ起こさない
4. 一覧の状態表示と作り直しの導線
5. `ANTHROPIC_API_KEY` を本体 worker のシークレットに登録する
6. デプロイ

**ロールバック**: 生成を起こす箇所を外せば、change 4 の状態に戻る。列は
残るが害はない。既存のメモと問答には触れない。

## Open Questions

- **Haiku で品質が足りるか。** 実際のメモで見てから判断する。足りなければ
  モデル名を差し替える（D3）。specs も作業の分け方も変わらない
- **「作成中」を諦める時間と、一覧を取り直す回数の具体値。** 実測して決める。
  どちらも上限があること自体は D9・Risks で決まっている
