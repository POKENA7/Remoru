## Context

動機と範囲は proposal.md を参照。画面設計は `docs/design-decisions.md`、デプロイ手順は `docs/deploy.md`。

**制約1: OpenNext の worker に cron を足せない。** 生成される worker は `fetch` だけを持ち、`scheduled` ハンドラを追加する口が無い（確認済み）。したがって定期実行は別の Worker に置くしかない。

**制約2: 先行実装は cron から本体を HTTP で叩いた。** その内部エンドポイントのために `/api/internal/(.*)` が認証から除外され、要求本文の `userId` を信じる作りになっていた。change 3 の D2・D3 はこの形を避けるために置いたものであり、ここで元に戻してはならない。

**制約3: `web-push` は Node.js 向けで Workers では動かない。** Workers の Web Crypto で VAPID を扱えるライブラリが要る。

**制約4: iOS はホーム画面に追加した PWA でしか通知を受け取れない。** ブラウザのタブでは届かない。実機で確かめるまで分からない領域が広い。

## Goals / Non-Goals

**Goals:**

- 決めた時刻に一度だけ、件数だけを伝えて呼び戻すこと
- 本体アプリに認証から除外する経路を1つも増やさないこと
- 届けるものが無い日は黙っていること
- 通知を切っても復習そのものは使えること

**Non-Goals:**

- 通知の内容の作り込み。件数だけでよい
- 配信の保証・再送・既読管理。届かなければ次の日に届く
- 通知以外の呼び戻し経路（メール等）
- 複数の通知時刻、曜日ごとの設定

## Decisions

### D1: cron worker は D1 を直接読み、自分で送る

`cron-worker/` を独立した Worker として置く。Cron Trigger を持ち、本体と**同じ D1 をバインド**し、購読情報を読んで自分でプッシュを送る。

```
cron-worker  ──読む──▶  D1  ◀──読み書き──  本体アプリ
     │
     └──送る──▶  プッシュサービス  ──▶  端末
```

**本体アプリへの HTTP 呼び出しをしない。** 内部エンドポイントも共有シークレットも作らない。先行実装が `/api/internal` を認証から除外することになった経路そのものを持たない。

*代替案*: 先行実装と同じく cron から本体の内部エンドポイントを叩く。却下。認証から除外する経路が生まれ、change 3 で塞いだ穴を自分で開け直すことになる。

*代替案*: OpenNext の worker に `scheduled` を足す。不可（制約1）。

### D2: 送信は Workers の Web Crypto で行う

`@block65/webcrypto-web-push` を使う。Cloudflare Workers を明示的に支援しており、VAPID の署名と本文の暗号化を Web Crypto で行う。

`web-push`（先行実装が使っていたもの）は Node.js 向けで、edge の Worker では動かない。

### D3: 1時間ごとに起きて、その時刻の利用者を探す

Cron Trigger は `0 * * * *`（毎時0分）。起きたら、利用者ごとに「その利用者の地域でいま何時か」を求め、指定時刻と一致する利用者だけに送る。

利用者の地域を持つ必要があるのはこのためである。UTC で一律に送ると、利用者から見た時刻がずれる。

**不正な地域名は、その利用者だけを飛ばして残りを続ける。** 一人ぶんの設定の壊れが全員の配信を止めてはならない（spec の要件）。

*代替案*: 利用者ごとに Cron を作る。不可。Cron Trigger は Worker 単位であり利用者ごとには作れない。

### D4: 「その日すでに送ったか」を記録する

利用者ごとに最後に送った日を保持し、同じ日に二度送らない。

Cron は毎時起きるので、時刻の判定だけでは境界で二重に送りうる。また Cloudflare の Cron は稀に二重に起動しうる。**記録で防ぐ。** 判定は「その利用者の地域での日付」で行う。

### D5: 通知には件数と先頭の問いを載せ、答えとメモ本文は載せない

本文は件数と、出題順で先頭にあたる問い（例:「今日は3枚 ／ 近所のパン屋の定休日は？」）。

**問いを載せるのは、通知を見た時点で想起が始まるからである。** 思い出せなければアプリを開く動機になり、思い出せればそれ自体が復習として成立する。件数だけの通知は「何かがある」としか伝えず、開く理由を作らない。

答えは載せない。見えた時点で想起の機会が消える。**メモの本文も載せない** — メモは問いの答えを含んでいることが多い（「近所のパン屋は火曜定休」は「定休日は？」の答えそのもの）。

「先頭」は出題順の先頭とする。出題順は次回出題日の古い順、同着は問答の識別子順であり（`review-session` の既存実装）、決定的に定まる。

*当初の判断*: 件数だけを載せ、問いも含めない、としていた。「答えが目に入ると想起の機会が失われる」という理由は正しいが、そこから問いまで禁じたのは飛躍だった。答えと問いは想起に対して逆向きに働く。

### D6: 購読は端末ごとに持つ

同じ利用者が複数の端末から購読しうる。購読は端末ごとに1件とし、利用者に紐づける。

配信で「もう有効でない」と示された購読は取り除く。取り除けなかったものがあっても、他の利用者への配信は続ける。

### D7: 通知の設定は復習タブの中に置く

下部タブは「メモ」と「復習」の2つのまま増やさない（`docs/design-decisions.md`）。通知の設定は復習タブから開ける場所に置く。

**通知を切っている状態が、後ろめたく見えないようにする。** 「オフ」と表示するだけで、有効化を促す文言を常時出さない。既存のトーン（責めない）と一貫させる。

### D8: 実機で確かめるまで分からない領域を明示する

自動で確かめられるのは、送信先を差し替えた配信の呼び出し（成功・期限切れ・その他の失敗）、時刻の判定、二重送信の抑止まで。

**次の4つは実機でしか確かめられない。** タスクに明示的に置く。

- 端末の許可ダイアログ
- Service Worker の登録
- 実際に通知が届くこと
- 通知をタップして復習が開くこと

### D9: 選べる時刻は 6〜23 時にする

夏時間を始める日、その地域には**存在しない時刻**が生じる（多くの地域で
02:00 が 03:00 に飛ぶ）。cron は毎時0分に起きて「その地域でいま何時か」を
求めるので、存在しない時刻を指定している利用者はその日だけ一致せず、通知が
来ない。年に1回、静かに1日ぶん落ちる。

飛ぶ時刻は世界のどの地域でも 00:00〜04:00 の範囲にあるため、**選べる時刻を
6〜23 時に絞ることで避ける**。判定側に例外を入れるより、選べないほうが単純で、
壊れる余地が無い。

深夜に呼び戻さないという product 側の判断とも向きが同じ。

*代替案*: 24時間すべて選べるようにし、存在しない時刻を検出して繰り上げる。
却下。判定が地域ごとの遷移規則に依存し、テストも書きにくい。得られるのは
「深夜2時に通知を受け取れる」ことだけで、割に合わない。

## Risks / Trade-offs

- **[iOS はホーム画面追加が必須]** ブラウザのタブでは通知が届かない。利用者がその制約を知らないと「壊れている」と受け取る → 設定画面でその旨を伝える。ただし完全な緩和にはならない
- **[デプロイ先が2つになる]** 本体と cron worker を別々に出す必要があり、片方だけ古いまま気づかない事故がありうる → `docs/deploy.md` に両方の手順を書く。D1 のスキーマを共有しているため、マイグレーションの適用漏れは cron 側の失敗として現れる
- **[VAPID の鍵を2箇所に登録する]** 本体と cron worker の両方に要る。片方だけだと購読はできるが届かない、という分かりにくい壊れ方をする → 手順書に明記し、デプロイ後に実際に届くことを確認するまで完了としない
- **[Cron の実行は保証されない]** Cloudflare の Cron Trigger は稀に遅れる・飛ぶ。通知が来ない日がありうる → この製品では許容する。届かなければ次の日に届く。配信の保証は Non-Goal
- **[通知の中身がロック画面に出る]** 問いがロック画面に表示されるため、端末を覗かれると内容が読まれる。日常の断片が主とはいえ、他人に見られたくないメモもありうる → 端末側の設定（ロック画面で内容を隠す）で対処できる。アプリ側の切り替えは設ける必要が生じてから足す。件数だけに戻す選択肢は、開く動機を失うため採らない
- **[自動で確かめられる範囲が狭い]** 通知まわりは実機に依存する部分が大きい → D8 のとおり、確かめられない領域を曖昧にせずタスクとして明示する。先行実装も同じ問題を抱え、手動確認の手順を README に残していた

## Migration Plan

1. テーブルを2つ追加する（通知設定、購読情報）
2. 本体に Service Worker、購読の受け口、設定画面を足す
3. `cron-worker/` を作り、同じ D1 をバインドする
4. VAPID の鍵を生成し、本体と cron worker の両方に登録する
5. 本体をデプロイし、実機で購読できることを確認する
6. cron worker をデプロイし、**実際に通知が届くことを確認する**

**ロールバック**: cron worker を停止すれば通知は止まる。本体側は Service Worker の登録を外し、設定画面を隠せば change 3 の状態に戻る。テーブルは残るが害はない。

## Open Questions

- 既定の通知時刻を何時にするか → 実装時に決めてよい。設定で変えられる
- 通知が届かない日が続いたときに気づく手段 → いまは無い。必要になってから考える
