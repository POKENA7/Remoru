## Why

change 3 で本番に出て、自分のスマホから使える状態になった。だが**まだ自分から開きに行かないと何も起きない**。

この製品の前提は「エビングハウスの忘却曲線に基づく間隔で**再提示する**」ことである。再提示の経路が無い限り、期日が来た問いは静かに溜まり続ける。change 2 の proposal に書いたとおり、自分で開きに行く復習と、呼ばれて開く復習は体験として別物であり、**後者こそがこの製品が成立するかどうかを決める**。

change 3 のタスク 7.4（数日使って日常に入るかを判断する）は未実施のまま閉じた。通知が無い状態での判断を待たずにここへ進むのは、**通知の有無で答えが変わる**からである。通知なしで続かなくても、それは製品の否定ではなく通知が必要だという根拠になる。

## What Changes

- **Service Worker を追加する。** change 3 で意図的に見送ったもの。プッシュの受信と、通知をタップしたときの遷移を担う
- **プッシュ通知の購読を受け付ける。** 許可を求め、購読情報を保存する。許可しない選択も尊重する
- **通知の時刻を利用者が決められるようにする。** 1日1回。設定画面と、利用者ごとの時刻・タイムゾーンを保持する仕組みが要る
- **独立した cron worker を追加する。** Cloudflare の Cron Trigger を持ち、1時間ごとに起きて、その時刻に通知すべき利用者を探して送る
- **復習が0件の日は送らない。** 中身の無い通知は出さない

### v1 と同じにしない点

先行実装も cron worker を持っていたが、**本体アプリの内部エンドポイントを共有シークレットで叩く**形だった。その結果 `/api/internal/(.*)` が認証から除外され、要求本文の `userId` を信じる作りになっていた。

この change では **cron worker が D1 を直接読み、自分でプッシュを送る**。本体アプリに内部向けの入口を作らない。認証から除外する経路も増えない。

### 今回やらないこと

| 除外するもの | 扱う change |
|---|---|
| 問と答の AI 生成 | change 5 |
| タグ、メモ詳細画面 | change 6 |
| メール通知 | 対象外 |
| 通知の内容の出し分け（何を出題するかの予告） | 対象外。件数だけ伝える |

## Capabilities

### New Capabilities

- `notification`: 利用者が復習の時間に呼び戻されること。通知を受け取るかどうかの選択、届く時刻の指定、届いた通知から復習へ入ること、そして届けるべきものが無い日は黙っていること

### Modified Capabilities

なし。既存 capability の要件は変わらない。

## Impact

**コード** — 本体アプリに Service Worker、購読の受け口、設定画面が加わる。あわせて `cron-worker/` を新設する。これは本体とは別の Cloudflare Worker であり、独自の `wrangler.jsonc` を持つ。

**データ** — 2つのテーブルを新設する。利用者ごとの通知設定（時刻・タイムゾーン・通知の可否）と、プッシュの購読情報。change 3 の design D1 で「通知の時刻やタイムゾーンが要る change 4 で、必要になった時点でテーブルを足せばよい」と判断したとおりになった。

**依存関係** — Workers 上で動くプッシュ送信のライブラリを追加する。`web-push` は Node.js 向けで Workers では動かない。

**秘密情報** — VAPID の鍵を追加する。本体と cron worker の両方に登録する必要がある。リポジトリには入れない。

**デプロイ** — デプロイ先が2つになる。本体と cron worker をそれぞれ出す必要があり、手順書の更新が要る。

**費用** — Cron Trigger は無料枠の範囲。通知の送信自体に費用はかからない。

**制約** — iOS ではホーム画面に追加した PWA でしか通知が届かない。ブラウザのタブで開いているだけでは受け取れない。この制約は利用者に伝える必要がある。
