- [x] 1.2 `review_schedules` テーブルを定義する（`quizItemId` / `nextReviewAt` / `state`）。`quizItemId` に外部キーと `ON DELETE CASCADE` を張る。`state` は JSON 文字列。検証: 同上
- [x] 1.3 メモを削除すると問答とスケジュールも消えることを、インメモリ SQLite に対するテストで確認する。検証: メモ・問答・スケジュールを作り、メモを削除したあと3つとも0件になること。**アプリ側で順に消す実装にしないこと**（design D5）

## 2. スケジューラ

design.md の D1〜D3 に対応する。この change の中心であり、ここが間違うと全部間違う。

- [x] 2.1 間隔表 `[1, 3, 7, 14, 30]` と `schedule(state, outcome, now)` を純粋関数として実装する。時計を内部で読まないこと。検証: 型チェックが通り、モジュールが HTTP・DB・フレームワークを import していないこと
- [x] 2.2 成功時の遷移をテストする。検証: 段階を 1日→3日→7日→14日→30日 と順に上がること、段階5に達したあとは30日を維持することを確認する
- [x] 2.3 失敗時の遷移をテストする。検証: 段階4（14日）で失敗すると次が1日後になり `recoverTo=2` が記録されること、その次に成功すると7日後になり段階1・2を経由しないことを確認する
- [x] 2.4 段階1で失敗した場合をテストする。検証: 次が1日後になり、復帰後も一度1日後に出ること（`recoverTo=0`）。design.md D3 に記した意図した挙動であることを確認する
- [x] 2.5 スケジューラの import 境界をテストで固定する。検証: スケジューラのモジュールが `next/*`、データベース、HTTP のいずれも import していないことを検査するテストが通ること。**レビュアーがいないので規約ではなく検査で守る**（design D2）
