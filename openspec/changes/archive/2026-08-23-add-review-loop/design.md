## Context

動機と範囲は proposal.md を参照。画面設計・配色・コピーは `docs/design-decisions.md` に確定済みで、ここでは蒸し返さない。

change 1 で存在するもの: `memos` テーブル（`userId` は固定値）、`POST/GET /api/memos`、単一画面のメモ投入と一覧、インメモリ SQLite のテストヘルパ。認証・通知・AI はいずれも未導入。

**制約1: スケジューラは差し替えられなければならない。** 固定間隔で始めるが、SM-2 系の適応アルゴリズムへ移す可能性が残っている。spec の「外部から観測できるのは次回出題日のみ」はこの制約の表現であり、境界が名目だけになると満たせない。

**制約2: 自己採点の2択が唯一の入力である。** 出題間隔はこの2値だけで決まる。入力の歪みは全体の歪みに直結する。

**制約3: 日付単位で動く。** 画面に出るのは「次は 8月26日」であり、時刻ではない。当日中の再出題は表現できない。

## Goals / Non-Goals

**Goals:**

- スケジューラを、差し替えが配線の変更だけで済む形に置くこと
- 自己採点の記録を再実行しても壊れないこと。通信は失敗するものとして設計する
- 復習ループの成立を判断できる最小の画面を揃えること

**Non-Goals:**

- 適応アルゴリズムの実装。今回は固定間隔のみ
- 問と答の編集。書き間違えたらメモごと削除してやり直す（change 6 でメモ詳細画面と共に）
- 出題順の最適化。期日が来たものを一定の順で出すだけでよい
- 復習の統計・履歴の可視化。達成率を出さない方針と両立しない

## Decisions

### D1: スケジューラは純粋関数で、時計を引数で受け取る

```
schedule(state, outcome, now) -> { state, nextReviewAt }
```

`outcome` は `{ recalled: boolean }`。**アルゴリズム固有の評点を境界に置かない。** 2択のUIはこの製品の決定事項なので、境界を評点にすると差し替え時にUIごと変えることになる。`recalled` は利用者から観測できる事実であり、どの算出方式でも意味が変わらない。

`now` を引数で受け取り、内部で時計を読まない。「3日後に出題される」をテストから決定的に検証するために必要である。

*代替案*: スケジューラが直接データベースを更新する。却下。純粋関数でなくなり、時間に依存するテストが書けなくなる。

### D2: 状態は不透明。公開するのは次回出題日だけ

`review_schedules` テーブルは3つの列を持つ。

| 列 | 誰が読むか |
|---|---|
| `quizItemId` | 全員 |
| `nextReviewAt` | 全員（出題対象の絞り込み、一覧の表示） |
| `state` | **スケジューラだけ**（JSON。他の層は読まない・書かない・分岐しない） |

`nextReviewAt` は state の公開された射影である。段階や係数は `state` の中に閉じる。SM-2 に差し替えるとき、変わるのは `state` の中身とスケジューラだけで、クエリも画面も変わらない。

この境界は**import 境界のテストで担保する**。スケジューラのモジュールが HTTP・セッション・データベース・フレームワークのいずれも import していないことを検査する。レビュアーがいないので、規約ではなく検査で守る。

### D3: 段階と復帰地点

`state = { stage, recoverTo }`。`stage` は間隔表 `[1, 3, 7, 14, 30]` の添字。

| 入力 | 遷移 | 次回 |
|---|---|---|
| 問答の作成 | `{stage:0, recoverTo:null}` | 1日後 |
| 成功（`recoverTo` なし） | `stage' = min(stage+1, 4)` | `間隔[stage']` |
| 成功（`recoverTo` あり） | `stage' = recoverTo`、`recoverTo = null` | `間隔[stage']` |
| 失敗 | `stage' = 0`、`recoverTo = max(stage-1, 0)` | **1日後** |

段階4（14日）で失敗した場合の軌跡:

```
段階3(14日)  失敗  → 次1日後   state={stage:0, recoverTo:2}
             成功  → 次7日後   state={stage:2, recoverTo:null}   ← 1日・3日を飛ばす
             成功  → 次14日後  state={stage:3, recoverTo:null}
```

段階1（1日）で失敗した場合は `recoverTo = 0` となり、復帰後も一度1日後に出る。失敗した段階を1回は通り直すことになるが、これは意図した挙動である。

### D4: べき等性は「どの出題に対する採点か」で担保する

クライアントは採点時に、**そのとき表示していた出題日**を一緒に送る。サーバーは保存済みの `nextReviewAt` と突き合わせ、一致しなければすでに採点済みとみなして何もせず成功を返す。

```
送られた出題日 == 保存済みの nextReviewAt  → 採点を適用し、日付を進める
送られた出題日 != 保存済みの nextReviewAt  → 二重送信。何もせず成功を返す
```

採点が適用されると `nextReviewAt` が動くので、同じ要求を二度送っても二度目は一致しない。**専用の履歴テーブルを持たずにべき等になる。**

*代替案*: 採点のたびに UUID を発行して重複を排除する。却下。テーブルが増え、クライアントが識別子を管理する必要が生じる。出題日はすでに画面が持っている値である。

*代替案*: 何もしない（べき等性を諦める）。却下。画面は失敗時に再実行を促す設計であり、再実行が間隔を二重に進めると記録が静かに壊れる。

### D5: 削除はデータベース側で連鎖させる

`quiz_items` と `review_schedules` に外部キーと `ON DELETE CASCADE` を張る。アプリ側で3つのテーブルを順に消す実装にしない。

途中で失敗すると、問答のない出題対象や、メモのない問答が残る。削除を1つのトランザクションで済ませられる形にしておくほうが安全である。

### D6: 画面は下部タブ2つに再編する

change 1 の単一画面は「メモ」タブの中身になる。「復習」タブが加わる。タブは2つのままで、増やさない。

問と答の作成は、メモ保存の直後にせり上がるシートとして出す。背後には保存されたばかりのメモを先頭に含む一覧が見えている（`docs/design-decisions.md` の画面2）。

### D7: テストの対象を絞る

| 対象 | 理由 |
|---|---|
| スケジューラの遷移表（D3 の全経路） | 純粋関数で、製品の中心。ここが間違うと全部間違う |
| べき等性（同じ出題日を2回送る） | 静かに壊れる種類の欠陥。実行して確かめる以外にない |
| 出題対象の絞り込み（期日前・期日後・問答なし） | 日付の境界は間違えやすい |
| import 境界（スケジューラの依存の向き） | D2 の担保 |
| 削除の連鎖 | データが残る欠陥は後から気づきにくい |

UI の網羅率は追わない。spec のシナリオはブラウザで一通り辿って確認する（`.learnings/active.md` L05）。

## Risks / Trade-offs

- **[2択では情報が落ちる]** SM-2 系は0〜5の評点を要求するが、`recalled: boolean` からは復元できない → 差し替え時は当面すべての成功を同じ評点として扱うことになる。これは**承知のうえの取引**である。手数の少なさを優先した結果であり、`docs/design-decisions.md` に記録済み。
- **[固定間隔が断片に合っているか未検証]** 1・3・7・14・30日は間隔反復で広く使われる値だが、「近所のパン屋の定休日」のような日常の断片に対して妥当かは誰も確かめていない → この change の目的がまさにその判断である。合わなければ間隔表を変える。表は1箇所にあるので変更は安い。
- **[当日中の再出題ができない]** 忘却曲線がもっとも急なのは直後だが、日付単位なので最短は1日後になる（制約3）→ 通知（change 4）が入るまで手立てがない。既知の限界として記録する。
- **[べき等性が出題日の一致に依存する]** 同じ問答が同じ日に2回期日を迎えることはないので衝突しないが、この前提は spec の「同一日のうちに再び出題しない」に支えられている → その要件が崩れるとべき等性も崩れる。両者は一体で扱う。
- **[判断が確定しない]** 自分で開きに行く復習と、通知に呼ばれる復習は別物である → この change の判断は「明確にダメなら早く捨てる」ためのもので、「いける」の確証には使わない。proposal.md にも明記した。

## Migration Plan

`quiz_items` と `review_schedules` を追加する。既存の `memos` は変更しない。change 1 で投入済みのメモは問答が未作成の状態として一覧に並び、後から作成できる。

**ロールバック**: 追加した2テーブルを落とし、画面を単一画面に戻す。`memos` に手を入れていないので、change 1 の状態に完全に戻る。

## Open Questions

以下は今答えなくても approach・タスク分解のいずれも変わらない。

- 間隔表 `[1,3,7,14,30]` は日常の断片に合っているか → 実際に使って判断する。合わなければ表を差し替える
- 出題対象が多い日の順序（古い順・ランダム・新しい順）→ 当面は次回出題日の古い順とする。不満が出たら変える
- 期日を大きく過ぎたもの（30日放置など）を特別扱いすべきか → 実際に放置してから考える
