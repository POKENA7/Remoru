## Context

動機は `proposal.md` の `## Why`、要件は `specs/` を参照。

**制約1: 下部タブは「メモ」と「復習」の2つのまま増やさない**（`docs/design-decisions.md`）。
タグの絞り込みも、メモ詳細も、この2つの中に収める。

**制約2: 一覧の行はすでに情報が多い。** 本文・問・次回出題日・作り直し・削除が
並んでいる（change 5 時点）。ここにタグと詳細への導線を足すと、行が破綻する。

**制約3: 提案の承認は「タグ名と件数だけ」と決まっている**（`docs/design-decisions.md`）。
どのメモに何が付くかを1件ずつ確認させると、手で付けるのと変わらない。

**制約4: 生成は1回ごとに課金される。** change 5 と同じ鍵を使う。利用回数の
上限はアプリ側に置かない方針（change 5 D8）。

## Goals / Non-Goals

**Goals:**

- メモが増えても目当てのものに辿り着けること
- タグを付ける手間が、書く手間を上回らないこと
- 提案が失敗しても、タグと復習が以前より悪くならないこと

**Non-Goals:**

- **1件のメモに複数のタグを持たせること**（D2）。戻せる形にはするが、
  この change では1つに絞る
- 複数タグの組み合わせによる絞り込み。単一選択で足りる
- タグの名前の変更・統合・削除の管理画面。まず付けて絞り込めることを確かめる
- タグによる復習の絞り込み。**復習は全件から出す**（spec の要件）
- タグの並び替えや色分け

## Decisions

### D1: タグは2つの表で持つ

`tags`（利用者・名前）と `memo_tags`（メモとタグの対応）に分ける。
同じ利用者の中で名前は一意にする。

*代替案*: `memos` に文字列の列で持つ。却下。絞り込みが部分一致になり、
「料理」で「料理酒」のメモが引っかかる。名前を直すと全行の書き換えになる。
**1メモ1タグにしてもこの問題は消えない。**

### D2: 1メモ1タグ。ただし**表の形は多対多のまま**にする

利用者の判断で、1件のメモが持てるタグは1つとする。複数持てると、一覧の行の
描き方、付け外しの操作、提案の承認の単位がそれぞれ複雑になる。

**ただし「1つ」を表の形で表現しない。** `memo_tags`（メモとタグの対応）は
多対多のまま置き、**1に絞るのはドメイン層の1箇所**にする。

| 1に絞る場所 | あとで複数に戻すとき |
|---|---|
| `memos` にタグの列を持つ | マイグレーションとデータ移行が要る |
| **対応の表＋ドメイン層の規則**（採用） | **規則を緩めるだけ。データはそのまま** |

上限は名前を付けた定数（`MAX_TAGS_PER_MEMO`）として1箇所に置き、付与の経路は
すべてそこを通す。緩めるときに触るのは、その定数と、それに依存する画面だけに
なる。

**すでにタグを持つメモに別のタグを付けたら差し替える。** 拒否して「外してから
付け直す」2手順にしない。1つしか持てない以上、操作の意味は「足す」ではなく
「選ぶ」であり、選び直しが1手で済まないのは不自然。

*代替案*: `memos` にタグの列を1つ持つ。却下。いま一番単純なのは確かだが、
複数に戻す可能性があると分かっているのに、戻すときのコストが一番高い形を
選ぶことになる。表が1つ増えるぶんの複雑さは、そのほとんどが結合の1行に収まる。

*代替案*: 表は多対多にして、上限をデータベースの制約で表す。却下。SQLite で
「1メモにつき1行まで」を宣言的に書くには `memo_tags.memo_id` を主キーに
するしかなく、それは結局「表の形で1つを表現する」ことになり、戻すときに
マイグレーションが要る。

### D3: メモ詳細は画面ではなくシートで出す

change 1 の問答シートと同じく、下からせり上がる。下部タブは2つのままで、
URL も増やさない（制約1）。

タグの付け外しと削除をここに置く。

*代替案*: 独立した画面に遷移する。却下。戻る操作の受け皿が要り、
下部タブとの関係も曖昧になる。詳細で行うのは付け外しと削除だけで、
シートに収まる。

### D4: 削除の導線を一覧から詳細へ移す

一覧の行にタグと詳細への導線が加わるため、**取り消せない操作を同じ行から外す**
（制約2）。誤って触れる余地を減らす。

*代替案*: 両方に置く。却下。同じ操作の入口が2つあると、どちらが正かの判断が
毎回必要になる。

### D5: 絞り込みは一覧の上に帯で出し、クライアント状態で持つ

選ばれているタグは URL に持たない。タブと同じ扱いにする。

絞り込みは**サーバー側で行う**（一覧の取得にタグを渡す）。クライアントで
絞ると、メモが増えたときに全件を毎回送ることになる。

### D6: 提案は「まとめて1回」で、押したときに待たせる

未分類が一定数たまったら一覧に帯を出す。押すと、**未分類のメモをまとめて
1回**モデルに渡す。

メモ1件ごとに呼ばない。費用が件数に比例し、承認の手間も件数分になる
（制約3・制約4）。

**待たせる。** 利用者が押して結果を待っている操作なので、応答後の枠に
預けると何も起きていないように見える。change 5 の作り直し（D5）と同じ判断。

*代替案*: 保存時に1件ずつ提案する。却下。制約3の「タグ名と件数で承認する」
形が成立しない。

### D7: 1回に渡すメモには上限を設ける

未分類が100件たまっていても、1回に渡すのは上限までとする。トークンが
際限なく増えるのを防ぐ。残りは次の提案で扱う。

上限の具体値は実測して決める（`## Open Questions`）。

### D8: 既存のタグ名を入力に含める

提案のたびに新しい名前が生まれると、タグが乱立して絞り込みの役に立たなく
なる。**すでにあるタグの名前を入力に渡し、当てはまるならそれを使わせる。**

### D9: 提案の出力はタグ名の文字列としてしか扱わない

change 5 D4 と同じ形。道具呼び出しで `{ tag: string, memoIds: string[] }` の
並びを受け取り、**タグ名は文字列として、メモの id は自分が渡したものとの
照合にのみ使う。** 知らない id が返ってきたら捨てる。

出力から処理を分岐させない。メモ本文がモデルへの入力に入るため。

### D10: 断られた提案は、次にたまるまで出さない

利用者ごとに「最後に断ったときの未分類件数」を持つ。それを一定数上回るまで
帯を出さない。

*代替案*: クライアント側（localStorage）で覚える。却下。端末を変えると
また出る。spec は「繰り返し示してはならない」と利用者について定めている。

### D11: 提案の失敗は静かに戻す

失敗を警告として出さない。帯が残り、あとでやり直せる状態にする。
既存のタグには触れない（`docs/design-decisions.md` の「責めない」トーン）。

**ただし失敗は記録に残す**（change 5 D6 と同じ）。

## Risks / Trade-offs

- **[提案がタグを乱立させる]** 呼ぶたびに違う名前が生まれると絞り込みが
  機能しなくなる → D8 で既存の名前を渡す。**それでも防ぎきれない**ので、
  実際に使って様子を見る。タグの統合は Non-Goal に置いてあり、必要になったら
  別の change で扱う
- **[1回の提案が高くつく]** 未分類のメモ本文をまとめて送るため、1回あたりの
  トークンは change 5 の生成より大きい → D7 の上限で頭を打たせる。呼ぶのは
  利用者が押したときだけで、自動では走らない
- **[承認が雑になる]** タグ名と件数だけで承認するため、中身は見ずに受け入れる
  ことになる → 受け入れたあとに詳細から外せることで担保する（spec の要件）。
  **これは意図した割り切り**であり、1件ずつ確認させない代償
- **[1タグでは足りない場面がある]** 「仕事」と「読書」の両方に当てはまる
  メモは、どちらか一方しか選べない → **戻せる形にしてある**（D2）。
  実際に困るかは使ってみないと分からないので、いま複数にはしない。
  8.3 で見る
- **[一覧の行が重くなる]** タグ・問・出題日・詳細への導線が並ぶ → 削除を
  詳細へ移して1つ減らす（D4）。それでも足りなければ、行の情報量は
  実装して見てから削る

## Migration Plan

1. 表を2つ追加する（タグ、メモとタグの対応）と、提案の状態を持つ表を1つ
2. タグの付け外しと絞り込み（サーバー側）
3. メモ詳細のシート。削除をここへ移す
4. 一覧にタグを出す。絞り込みの帯
5. 提案（まとめて1回・承認はタグ名と件数）
6. デプロイ。鍵は change 5 のものをそのまま使う

**ロールバック**: 提案の帯と絞り込みを隠せば、タグは付いたまま無害になる。
削除の導線は一覧に戻せる。表は残るが害はない。

## Open Questions

- **帯を出す未分類の件数と、1回に渡すメモの上限。** 実測して決める。
  どちらも上限があること自体は D6・D7 で決まっており、specs も作業の
  分け方も変わらない
- **提案で付いたタグの精度。** 実際のメモで見てから判断する。悪ければ
  D8 の入力の与え方を変える
