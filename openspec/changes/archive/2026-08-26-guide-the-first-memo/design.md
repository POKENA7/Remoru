## Context

動機は proposal.md を参照。要件は `specs/first-run/spec.md`。

いまの初回は次のようになっている。

```
メモタブ
  入力欄       但し書き「いま、覚えておきたいこと」
  一覧         「まだ何もありません」        ← 現状の報告だけ
復習タブ
  「今日はありません」
  「通知の設定」  ← 通知の許可を求める唯一の入口
記録タブ
  「まだありません」
```

制約が3つある。

1. **`next_review_at` は問答と一緒に決まる**（`lib/quiz-items.ts`）。メモを
   保存しただけでは出題日が無く、告げる内容が存在しない。
2. **生成はメモの保存の応答を返したあとに走る**。完了は自動では届かず、
   `app-shell.tsx` が「作成中」が残る間だけ一覧を取り直している。
3. **復習の間隔は未確定事項**（`docs/intent-statement.md`）。固定間隔のまま
   とは限らないので、文言が間隔を前提にすると、変えた日に嘘になる。

## Goals / Non-Goals

**Goals:**

- 初回に足りないものを、説明ではなく**利用者自身のメモの上で起こること**で埋める
- 通知の許可を、何のための通知か分かっている位置で1度だけ差し出す
- 一度使い方を知った人には、二度と出さない

**Non-Goals:**

- 紹介画面・チュートリアル・手順の一覧
- 復習タブと記録タブの空状態に手を入れること（初回の導きは1本に絞る）
- 通知の時刻をこの場面で選ばせること（既定の時刻があり、設定で変えられる）

## Decisions

### D1: 初回かどうかを、利用者ごとに憶える

持ち物が0件かどうかでは、**2つの状態が区別できない**。

| | メモ0件 | 使い方を知っている |
|---|---|---|
| 初めて開いた | ○ | × |
| 全部消した | ○ | **○** |

全部消した人はもう使い方を知っている。誘いを出し直すのはおかしい。
`tag_suggestion_state` と同じ形で、利用者ごとに1行持つ。

```
first_run_state
  user_id    PRIMARY KEY
  guided_at  初回の導きを終えた時刻。終えていなければ null
```

**端末ではなく利用者に紐づける。** 使い方を知っているのは人であって端末では
ない。localStorage に置くと、機種を変えるたびに説明が戻ってくる。

#### この判断は確定事項を覆している

`docs/design-decisions.md` に「**「初回だけ表示する」形は採らない**」とある。
理由は2つ挙げられていた。

| change 8 が挙げた理由 | ここでの当否 |
|---|---|
| 見たかどうかの状態を持つ必要がある | **その通り。** 表を1つ増やす費用を払う |
| 初回に読んでいる保証が無い | **誘いには当たらない。** 導きを終えるまで何度でも出る |

change 8 が想定していたのは**説明文**を1度だけ出す形だった。ここで1度きりに
するのは説明ではなく、**そのメモに起きたことの提示**である。読み落としても
同じ内容は詳細（次回の出題日）と通知の設定に残っている。

覆すからには理由を残す。`docs/design-decisions.md` に書き足す（tasks 6）。
**理由の無い制約は、確かめずに従われる**（change 10 でタブを3つにしたときの
学びと同じ）。

### D2: 空の一覧には何も足さない

当初は空状態に誘いの一行を置く設計だった。やめた。

入力欄の但し書きが既に「いま、覚えておきたいこと」と言っており、書く内容は
そこで足りている。残る「書いたら何が起こるか」は**書いた直後のガイドが
実物で示す**ので、書く前に言葉で約束しても二度手間になる。しかも書く前の
約束は確かめられない。それは紹介画面と同じ性質である。

```
まだ何もありません   ← そのまま残す
```

導きは**1本だけ**にする。空の一覧と書いた直後の2箇所に置くと、change 8 で
削った「同じことを二度言う」形に戻る。

### D3: 告知は、出来上がった問答を持つメモの行に出す

一覧の上に帯として出すと、どのメモの話か分からない。**その人が書いた1件の
すぐそば**に出す。

```
┌────────────────────────────────┐
│ 入力欄                          │
├────────────────────────────────┤
│ 味噌汁は沸騰させない             │
│ タグなし                    ●   │
│ ┌────────────────────────────┐ │
│ │ 明日、まだ覚えているか       │ │  ← このメモの下に1度だけ
│ │ 尋ねてもいいですか？         │ │
│ │ [ いいよ ]                   │ │
│ └────────────────────────────┘ │
└────────────────────────────────┘
```

**文が主語を言わずに済む。** 「まだ覚えているか」が何について言っているかは、
真上にメモがあることで決まる。一覧の上に帯として出すと同じ文が宙に浮き、
何を指すのか書き足さなければならなくなる。

**ここでは日付を言う。** 誘い（D2）と違い、この時点では `next_review_at` が
決まっている。**実データから作るので嘘にならず**、しかも1日後に確かめられる。
紹介画面との違いはここにある。

誘いと告知は対になっている。誘いが約束し、告知が日付を入れて返す。

```
明日、まだ覚えているか尋ねてもいいですか？   [ いいよ ]
^^^^ 実データ
```

「まだ」は時間が経ったことを含む。書いた直後に問われるのではないと分かる。

**告知は問いかけにする。** 「いいよ」で答えられるので、文とボタンが1つの
会話になる。「知らせてもらう」のような機能名のラベルより、何に同意するのかが
文そのものから分かる。

ただし**通知を差し出せないときは言い切りに戻す**（通知に対応しない端末、
鍵の無い環境）。問いかけたまま答える手段が無いと、問いだけが残る。

### D4: 通知はその場で求める。設定画面へ飛ばさない

飛ばすと、**何のための通知かが分かっている状態が失われる**。設定画面には
時刻の選択と現在の状態があり、いま要らない判断を増やす。

時刻は既定値で購読する（`notification` の「時刻を指定していない状態で許可
する」）。あとから設定で変えられる。

購読の処理は `app/notification-settings.tsx` の中にあるので、**呼べる形に
切り出す**。画面から切り離すだけで、処理そのものは変えない。

### D5: 「繰り返し求めない」は、導きが1度きりであることで満たす

差し出しは告知の中にあり、告知は利用者ごとに1度しか出ない（D1）。したがって
**断りを憶える仕組みは要らない**。

当初は「閉じた」を localStorage に置く案だった。`Notification.permission` は
閉じただけでは `default` のままで、問答ができるたびに出てしまうためである。
D1 を利用者ごとの記録にしたことで、この問題そのものが消えた。

設定を自分から開いて有効にする経路は常に残る（`notification` の要件）。

### D6: 生成に失敗したら黙る

失敗したメモには一覧に既に印が出ており、詳細に「問と答をつくる →」がある。
ここに初回だけの案内を足すと、**失敗の説明が初回の第一印象になる**。
黙って、既にある経路に任せる。

**導きも終えない。** 失敗した人はまだ仕組みを見ていないので、次に問答が
できたときに告知が出る。

### D7: 答えたことは一覧の外で持つ

**メモの一覧はタブの切り替えとメモの詳細で unmount される。** 告知の中に
「答えた」を持つと、離れて戻ったときに同じ問いがもう一度出る。

この穴は既に2度踏んでいる。書きかけの本文が消え、受け取ったタグの提案が
消えた（提案は取り直しにモデルの呼び出し＝課金が要る）。**症状は毎回
違って見えるが、原因は同じ**なので、検査で並べて固定する
（`app/unmount-boundary.test.ts`）。

### D8: 告知の日付は `next_review_at` から作る

「明日」を手で書くと、間隔が変わった日に静かに嘘になる。差から組み立てる
小さな純関数を置く。

```
lib/first-run-text.ts
  INVITATION                        誘いの一行（間隔を口にしないので固定）
  announcementText(nextReviewAt, now) → 「明日」「N日後」を差から作る
```

判定は日境界で行う。時刻で引くと、23時に書いたメモが「0日後」になる。
既存の `startOfReviewDay`（`lib/review-scheduler.ts`）と同じ境界を使う。

## Risks / Trade-offs

- **表が1つ増える** → `tag_suggestion_state` と同じ形なので、書き方も
  移行も既存の型に収まる。列は2つ。
- **生成が数十秒かかると、誘いと告知の間が空く** → 「作成中」の表示が既に
  あり、`app-shell` が最大8回まで取り直す。この change では触らない。
- **告知を読み落とすと、二度と出ない** → 同じ内容はメモの詳細（次回の
  出題日）と通知の設定に残る。失われるのは「気づく機会」であって情報ではない。
- **一覧を絞り込んでいると0件になり、誘いが出る** → 絞り込み中の空は
  「このタグのメモはありません」で別に分岐している。誘いは絞り込みが
  外れているときだけに限る。
- **通知に対応しない端末では告知だけが出る** → 出題日は真なので、告知だけ
  出るのは正しい。差し出しの有無を分ける。**導きは終える**（出題日は見えた）。
