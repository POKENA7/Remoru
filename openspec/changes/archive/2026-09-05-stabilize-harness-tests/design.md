## Context

動機と実測値は proposal.md の `## Why` を参照。ここでは設計を選ぶのに必要な
制約と、調査で分かった足場の性質だけを述べる。

**現状**: `vitest.config.ts` は単一の設定で、`**/*.test.ts` 47 ファイル・558 件を
既定の並列（`maxWorkers` = CPU 数）で走らせる。うち `scripts/harness/` の 5 ファイルは
性質が違い、1 件ごとに `spawnSync` で**リポジトリ全体の検査**を起動する。

**制約 A: 赤の意味が 1 つでなければならない。** これらのテストが赤いとき、
それは「検査が違反を見逃した」を意味しなければならない。「機械が忙しかった」でも
赤くなるなら、赤を見た人は毎回どちらかを調べることになり、やがて調べなくなる。

**制約 B: 検査の中身を緩めてはならない。** `checks.test.ts` 冒頭のコメントが
理由付きで固定している 3 点 —— 一時ファイルは**リポジトリの中**に置く（外だと
`check:*` の入力に入らない。L09 と同じ罠）、置き場の名前に**ドットを付けない**
（TypeScript の `**` がドットで始まるディレクトリを辿らないため、`.harness-tmp`
では `check:types` だけ緑のままだった）、`--max-diagnostics=none` を外さない
（既定の 20 件で打ち切られると注入したファイルが隠れる）—— は、どれも
「一度これで検査が緑のまま何も守らなくなった」実測から来ている。触らない。

**制約 C: 待ち時間が長い仕組みは外される**（`add-deterministic-harness` design
制約 4 を引き継ぐ）。テスト全体の所要時間を大きく延ばす解は採れない。

**調査で分かった足場の性質（Vitest 4.1.11 で実測）**:

- `fileParallelism` と `maxWorkers` は**トップレベル専用**で、project ごとには
  指定できない（`UserConfig` にはあるが project の設定型には無い。browser 設定に
  ある `fileParallelism` は deprecated）。project 単位で並列を切ることはできない
- `poolOptions.forks.singleFork` は Vitest 4 で**削除された**
  （`DEPRECATED  test.poolOptions was removed in Vitest 4`）
- `sequence.groupOrder` は **project ごとに指定できる**。番号の小さい group から
  順に走り、同じ番号の project は同時に走る

## Goals / Non-Goals

**Goals:**

- `scripts/harness/*.test.ts` が赤いとき、それが**検査の欠陥だけ**を意味すること
- 時間の予算を、**実測したコスト**から決めること。既定値をそのまま使わないこと
- 同時に走っている別の vitest と、注入用の一時ファイルを取り合わないこと

**Non-Goals:**

- 注入テストを速くすること。1 件につき検査を 2 回起動するのは D10 の要求
  （注入した状態と取り除いた状態の両方を見る）であって、削れる無駄ではない
- CI の実行時間の最適化。今回は安定性だけを見る
- 他のテストの走らせ方を変えること

## Decisions

### E1: `app` / `harness` の 2 project に分け、`harness` にだけ別の時間予算を与える

`vitest.config.ts` に `projects` を置く。`app` は `**/*.test.ts` から
`scripts/harness/**` を除いたもの、`harness` は `scripts/harness/**/*.test.ts`。
`harness` にだけ `testTimeout` / `hookTimeout` を与える。

分ける理由は、**この 2 群はコストの桁が違う**からである。app 側の 553 件は
純粋な単体テストで、5 秒を超えたら本当に何かが壊れている。harness 側の 5 件は
外部プロセスを起動するので、秒単位が正常である。同じ予算を当てると、
どちらかが必ず間違った予算になる。

*代替案 1*: 設定を分けず、`testTimeout` をリポジトリ全体で上げる。却下。
app 側で無限ループに入ったテストが 5 秒ではなく 60 秒かけて落ちるようになる。
**予算は、そのテストが何をしているかに合わせる。**

*代替案 2*: `it(..., { timeout: N })` を各テストに個別に書く。却下。新しく足した
注入テストに書き忘れると、そこだけ既定の 5 秒に戻る。**忘れると静かに壊れる
経路を作らない**（制約 1）。project 単位なら、`scripts/harness/` に置いた時点で
自動的に適用される。

### E2: 予算は 60,000ms。実測の最悪値の約 5.5 倍に取る

| 条件 | `check:types` の注入テスト |
|---|---|
| harness だけ | 1,561ms |
| フルスイート並列 | 4,440〜5,623ms |
| フルスイート + `next build` | 7,851ms |
| フルスイート + `next build`（別の日） | **13,396ms** |
| CPU を 3 倍過負荷（16 プロセス） | 8,892ms |

最悪の実測は 13,396ms である。**倍数ではなく、はっきり桁の違う値**を取る。
4 倍程度だと、CI の遅いランナーや将来 `check:types` が 3 段になったときに
また同じ調査を繰り返すことになる。

**予算を上げても待ち時間は 1 ミリ秒も増えない。** 実装中に実測して分かった:
`spawnSync` は**同期呼び出しなのでワーカーをブロックし、vitest の testTimeout
では中断できない**。予算 5,000ms のテストに `spawnSync("sleep", ["15"])` を
置いたら、15,016ms きっちりブロックしてから「Test timed out in 5000ms」と
報告された。実際に 284,896ms かかった注入テストも観測している（予算 60,000ms）。

つまり `testTimeout` は**打ち切る仕組みではなく、事後に赤くする閾値**である。
待ち時間を決めるのは検査そのものの所要時間であって、予算ではない。
当初ここに「代償は 5 秒ではなく 60 秒待つこと」と書いたが、**それは誤り**だった。
予算を上げることの代償は、この設計には無い —— 変わるのは「何秒までを緑と
みなすか」だけである。制約 C（待ち時間）にも抵触しない。

裏を返すと、**予算をいくつにしても「機械が忙しすぎた」赤は無くせない**。
284,896ms の観測がそれで、60 秒でも 600 秒でも、そこまで遅い機械では赤くなる。
予算が消すのは**再現性のある赤**（5 秒は普通の負荷でも超える）であって、
病的な過負荷ではない。そこは残る限界として受け入れる。

*代替案*: 予算を上げず、走らせ方の制御だけで間に合わせる。却下。E3 で試したが、
実測で差が出なかった。

### E3: 走る順序は変えない（`sequence.groupOrder` は入れない）

**当初は入れる決定だった。実装中に測ったら効果が無かったので、撤回する。**

案は、`app` を group 0・`harness` を group 1 にして、リポジトリ全体の検査を
起動する重い 5 ファイルが app の 42 ファイルと CPU を取り合わないようにする、
というものだった。理屈は通っている。

最初の測定では、フルスイートでの `check:types` 注入テストが 5,623ms → 2,648ms に
下がって見えた。**これは誤読だった。** 2 回の実行はマシンの負荷が違っており、
設定の差ではなく負荷の差を測っていた。

同一条件で 6 回ずつ A/B を取り直した結果（CPU 負荷 8 プロセスを常時かけた状態）:

| | harness 最大値（6 run） | 中央値（外れ値を除く） |
|---|---|---|
| groupOrder なし | 937954 / 1577 / 1739 / 2066 / 1278 / 1232 | 1,658ms |
| groupOrder あり | 1236 / 1435 / 1676 / 940857 / 1248 / 1306 | 1,371ms |

差は約 290ms で、実行ごとのばらつきに埋もれる。**約 938 秒の外れ値が両方に
1 回ずつ出ている**ことも重要で、これは設定ではなくマシン側の要因である。

理由は、app 側のテストが速すぎて**そもそも競合が起きていなかった**ことだと考える。
42 ファイルは純粋な単体テストで、CPU を長く占有しない。

したがって入れない。**測って効かなかったものを「害が無いから」で残すと、
次に同じ問題を見た人が「順序制御が効いている」と誤解する。** 効いているのは
予算（E2）だけである、という状態を設定からも読めるようにしておく。

*代替案*: `fileParallelism: false` を harness project に付ける（そもそもの当初案）。
**できない。** Vitest 4 では project ごとに指定できず、トップレベルに書くと
47 ファイル全部が直列になる（制約 C 違反）。`poolOptions.forks.singleFork` も
Vitest 4 で削除されている。この確認が、順序・並列度の制御に望みを賭けない
根拠にもなっている。

### E4: 注入用の一時ファイルの置き場を、プロセスごとに分ける

現在の `checks.test.ts` は `harness-tmp/` の下に `mkdtemp` で毎回別のディレクトリを
作るが、`afterEach` が **`harness-tmp/` を丸ごと消す**。同時に別の vitest が
走っていると、相手の注入ファイルを検査の途中で消してしまう。

門（PreToolUse / Stop）は `check:test` を走らせるので、これは仮想の話ではない。
`checks.test.ts` 自身のコメントが「vitest の中から vitest が走る場面が実際にある」と
書いている。消された側は `expect(injected.status).not.toBe(0)` で落ちる ——
**制約 A が禁じている「検査以外の理由で赤くなる」経路**である。

置き場を `harness-tmp/p<pid>/` にし、`afterEach` はその下だけを消す。`harness-tmp/`
自体は空のときだけ片付ける。名前にドットを付けないことと、リポジトリの中に置くことは
そのまま（制約 B）。

*代替案*: `afterEach` をやめて `withInjected` の後始末だけに頼る。却下。テストが
途中で throw したときに注入ファイルが残り、以後の検査が**ずっと赤い**状態になる。

### E5: CI（`.github/workflows/ci.yml`）は変更しない

CI は `npm run check` を呼ぶだけで、検査の中身を持たない（D12）。今回の修正は
`vitest.config.ts` の中で完結するので、CI に書くことは無い。**定義が 2 か所に
あると必ずズレる**という D12 の判断をここでも守る。

CI で直ったことは、ワークフローを書き換えることではなく**緑で通ること**で確かめる。

## Risks / Trade-offs

- **[予算 60 秒が、本当に固まった検査を隠す]** → 隠さない。`spawnSync` は
  testTimeout で中断できないので（E2）、検査が固まれば予算の値に関係なく
  その時間だけブロックし、最後は赤くなる。予算が変えるのは閾値だけである。
  app 側は 5 秒のままなので、**普段書くテストの体感も変わらない**
- **[`projects` の導入で、走る対象が静かに減る]** → これが一番こわい。include の
  書き間違い 1 つで、あるディレクトリのテストが**緑のまま走らなくなる**。
  対策: 変更の前後で**テスト件数とファイル数が一致すること**を数で確かめる
  （現在 47 ファイル / 558 件）。タスクに検証条件として書く
- **[病的な過負荷では、予算をいくつにしても赤くなる]** → 実測で 938 秒かかった
  実行が 12 回中 2 回あった（CPU を 2 倍過負荷にした人工的な条件）。これは
  予算では消せない。**残る限界**として受け入れ、そういう赤を見たときは
  マシンの負荷を先に疑う手がかりとして、この節を残す
- **[この修正自体が、検査を検査でなくする]** → L06 が言っているのはまさにこれである。
  時間の予算を上げるだけなら assert は変わらないが、**変わっていないことを
  主張だけで済ませない**。タスクで、検査が見逃す側の違反（`biome.json` で
  `harness-tmp` を無視させる）を 1 つ注入し、注入テストが**赤くなること**を
  確かめてから採用する
- **[`harness-tmp/p<pid>` が残骸として溜まる]** → `harness-tmp/` は `.gitignore`
  済みで履歴には入らない。ただし残ると `check:*` の入力に入り続けるので、
  空のときは親も片付ける

## Migration Plan

段階は無い。`vitest.config.ts` と `checks.test.ts` を変え、`npm run check` が
通ることと CI が緑になることで完了とする。戻すときは 2 ファイルを revert すれば
元の挙動に戻る（設定以外の状態を持たない）。
