## Context

動機と線引きは `proposal.md`、要件は `specs/` を参照。

**制約1: このアプリは達成率・連続記録・順位を出さない。** `docs/design-decisions.md`
と `review-session` の spec が名指しで禁じている。**分母を持つものが責める**、
という線引きで今回は通す。

**制約2: 復習の履歴を持っていない。** change 2 が意図的にそうした。二重採点の
防止は `occurrenceAt` の比較で行っており、**履歴テーブル無しでべき等**に
なっている。

**制約3: 下部タブは2つと決まっていたが、理由が書かれていない。**
`docs/design-decisions.md` の表に1行あるだけで、根拠の記述が無い。3つの change
がこれに形を合わせてきた。

**制約4: 説明文を増やさない**（change 8）。新しい画面に使い方の説明を添えない。

## Goals / Non-Goals

**Goals:**

- 覚えてきた量を、責めない形で見せること
- 想起の出来事を残し、あとから辿れるようにすること
- 既存の復習・通知・タグの仕組みに触れないこと

**Non-Goals:**

- 時系列のグラフ。**記録は残すが、この change では出さない。** まず量と層で
  足りるかを見る
- 達成率・連続記録・順位。制約1
- 成功指標の判定。測れるようにはなるが、閾値を決めるのは別の話

## Decisions

### D1: 下部タブを3つにする。理由を書き残す

「メモ／復習／記録」。`docs/design-decisions.md` の1行を、**理由付きで**更新する。

**元の決定に理由が無かったことが、更新の根拠である。** 何を守るための制約か
分からないまま3つの change が形を合わせてきた。守っていたのはおそらく
「アプリを小さく保つこと」だが、アプリはいま**書く・復習する・振り返る**の
3つのモードを持っており、振り返りは復習の一部ではない。

*代替案*: 復習タブの中に置く。却下。**作業しに来た瞬間にしか目に入らない。**
振り返りはそのタイミングではない。

*代替案*: 完了画面に置く。却下。`review-session` の「完了の提示」は
**まさにその画面に対して**継続を促す指標を禁じている。置くなら要件の
書き換えになり、筋が悪い。

タブ名は「記録」。他の2つが漢字なので、ひらがなだと浮く（`docs/design-decisions.md`
の表記規則：名詞は漢字）。

### D2: 累計と層を並べる。**性格が逆であることが要点**

| | 何を表すか | 動き |
|---|---|---|
| 累計「N回 思い出しました」 | 積み上げてきたこと | **減らない** |
| 層（1週間／1か月／3か月以上） | いま持っているもの | 減りうる |

累計だけだと現在を映さない。層だけだと、忘れたときに全体が目減りして責める
形になる。**下が動いても、上が守る。**

### D3: 層は現在の出題間隔で分類する

「1週間以上」の意味は「1週間空けても思い出せる」であり、スケジューラの段階が
そのまま該当する。

| 段階 | 間隔 | 層 |
|---|---|---|
| 0, 1 | 1日, 3日 | （下の層に入らない） |
| 2 | 7日 | 1週間以上 |
| 3 | 14日 | 1週間以上 |
| 4 | 30日 | 1か月以上 |

**3か月以上の層は、いまの段階だけでは作れない。** 最長の間隔が30日なので、
段階からは「1か月以上」までしか出ない。3つ目の層を出すなら、**その問答を
どれだけ長く落とさずに持っているか**（記録から数える）になる。

→ `## Open Questions`。**層をいくつにするかは、実装して数を見てから決める。**

*代替案*: 実際の経過時間で分類する。却下。「覚えている期間」と「思い出せる
間隔」は別物で、後者のほうが spec の意味に近い。

### D4: 間隔は「次回出題日 − 最後に採点した日」で求める

**スケジューラの段階を読んではならない。** `review-scheduling` の spec が
「内部状態を capability の外へ観測可能な形で公開しては MUST NOT ならない。
外部から観測できるのは次回出題日のみ」と定めている。

代わりに、公開されている値と今回足した記録から導く。

```
間隔 = 次回出題日 − 最後に採点した日
```

**記録の無い問答は数えない。** 当初は「無ければ問答を作った日」を起点に
する設計だったが、`review_events` は change 10 で作った表なので、
**それ以前の問答はすべて「採点済みなのに記録が無い」状態にある**。作成日を
起点にすると、間隔ではなく**問答の古さ**を測ってしまい、60日前のメモを
今日「忘れてた」した直後でも「1か月以上」に数えられる。

一度も採点していない問答は必ず間隔1日でどの層にも入らないので、外しても
失うものは無い。

これは回避ではなく、**より良い形**である。次回出題日はどの算出方式でも
必ず存在するので、**SM-2 系に差し替えてもこの計算はそのまま動く**。
spec が「間隔の算出方式は将来差し替えられる」ために守ろうとしていたのは、
まさにこれだった。

*代替案*: スケジューラに `intervalDaysOf(state)` を足して公開する。却下。
spec の MUST NOT に正面から反する。しかも算出方式を差し替えたとき、
この関数の意味が変わる。

### D5: 記録は更新のあとに残す。順序で倒れ方を選ぶ

D1 は対話的なトランザクションを持たず、テストで使う better-sqlite3 の
ドライバは `batch` を持たない。**両方で動く原子的な書き方が無い**ので、
順序で倒れ方を選ぶ。

| 順序 | 途中で落ちたとき |
|---|---|
| 記録 → 更新 | 記録が二重になり、間隔が負になって層から消える |
| **更新 → 記録**（採用） | 記録が1件失われるだけ。押し直しは二重送信として弾かれる |

更新が `next_review_at` を動かすので、そこまで通れば押し直しは `occurrenceAt`
の不一致で弾かれる。**べき等性を持っている側を先に置く。**

### D6: 記録は出来事の表として持つ。既存のべき等性には触れない

`review_events`（いつ・どの問答・思い出せたか）を足す。

**二重採点の防止は `occurrenceAt` の比較のまま変えない**（制約2）。記録が
増えたので記録側で見ればいい、と後から思いつくと、**動いているものを壊しに
いく**ことになる。記録は足すだけで、判定には使わない。

問答が消えれば記録も消える（外部キーの連鎖）。メモを消すと問答が消え、
記録も消える。

*代替案*: 累計の列を1つ足すだけ。却下。今日の画面はそれで足りるが、
**時系列も成功指標も永久に作れなくなる。** 利用者が将来性を理由に表を選んだ。

### D7: この change では時系列を出さない

記録は残すが、画面には出さない。**まず量と層で足りるかを見る。** 足りなければ
次の change で足せる——記録があるので、あとから作れる。

### D8: 何も無いときに責めない

一度も復習していない利用者には、まだ何も無いことだけを示す。「はじめましょう」
のような促しを置かない（制約1・制約4）。復習が0件のときの「今日は、なし」と
同じ調子にする。

## Risks / Trade-offs

- **[タブが増えると、数字を見に行く動機が前に出る]** 常時見えるタブは、
  リンク1本より強い誘いになる。**分母が無い**ことが唯一の歯止めなので、
  ここが崩れると成績表になる → 累計が減らないことと、達成率を出さないことを
  spec の MUST NOT として書いた。破ると検査ではなくレビューで気づく形なので、
  **完全な防止ではない**
- **[3か月以上の層が作れないかもしれない]** D3 のとおり、段階だけでは
  1か月までしか出ない → 層の数は実装して決める。2つでも成立する
- **[記録が増え続ける]** 復習1回につき1行。1日10件でも年3650行で、いまの
  規模では問題にならない。消えるのは問答が消えたときだけ
- **[「記録」タブが1画面しかない]** 中身が薄い状態で常設の場所を取る →
  時系列（D7）を後から足す前提。薄いままなら畳む判断もありうる

## Migration Plan

1. 記録の表を足し、採点のときに残す
2. 累計と層の読み取り
3. 記録タブと画面
4. `docs/design-decisions.md` を更新（タブの数＝理由付き、分母の線引き）
5. デプロイ

**ロールバック**: タブと画面を外せば、記録が残るだけの無害な状態に戻る。

## Open Questions

- **層をいくつにするか。** 段階だけでは「1か月以上」までしか作れない（D3）。
  3つ目を出すなら記録から数えることになる。**実装して実際の数を見てから決める。**
  specs も作業の分け方も変わらない
- **累計が「思い出せた回数」だけでよいか。** 思い出せなかった回数も記録には
  残るが、画面には出さない前提。使ってみて判断する
