# 学び

- 学びは「**規則** + **それを生んだ出来事**」で書く。規則だけの記述は残さない（出来事がないと、後で残すか消すかを判断できない）
- 学びを適用したコミットには `Learning: LNN` の行を1つ足す
- 12件を超えたら棚卸を起動する（手順は `.learnings/archive.md` の冒頭）

- **[L01] `rm` と `cp` は対話モードを外して呼ぶ**
  このマシンの zsh は `rm` が対話モードにエイリアスされている。change 1 で確認待ちに気づかず、コマンドが2分間ハングしてタイムアウトした。change 16 で `cp` も同じで、`cp -f` を付けても「overwrite? (y/n [n])」で止まり、退避したファイルを戻せなかった（`-f` はエイリアスの `-i` を打ち消さない）。
  `rm -f` を使う。`cp` は `command cp` で呼ぶ。

- **[L02] 既存ファイルの上書きは `>|`**
  `noclobber` が有効なため `cat > file` が「file exists」で失敗する。change 1 で2回踏み、どちらも heredoc の中身が丸ごと実行されずに黙って消えた。
  上書き意図があるときは `>|` を使う。

- **[L03] headless Chrome の配色切替は CDP で行う**
  `--blink-settings=preferredColorScheme` も `--force-dark-mode` も効かず、ライト用とダーク用に撮った2枚がバイト単位で同一（219056 bytes）になった。フラグは静かに無視される。
  `Emulation.setEmulatedMedia` を CDP 経由で使う。

- **[L04] 配色の性質を主張する前に実測する**
  ダークモードを「暖色ベースにした」と報告したが、レンダリング結果から色相を測ったら背景は257＝紫だった。意図と結果が逆方向だった。
  主張の前に、計算値で確かめる。

- **[L05] spec のシナリオはブラウザで一通り辿る**
  単体テスト18件が全て緑でも、空白のみで保存を試した後のエラーが1001文字入力時にも残り続ける欠陥があった。ブラウザでシナリオを順に辿って初めて見つかった。
  実装が終わったら、spec のシナリオを画面上で1つずつ確認する。

- **[L06] 検査は、違反をわざと入れて赤くなるまで検査ではない**
  change 3 で、実鍵が履歴に無いことを見る grep が `.env.example` のプレースホルダ自身に一致し、`createRouteMatcher` を禁じる検査がその上のコメントに一致した。2回とも常に緑で、何も守っていなかった。
  検査・ゲートを書いたら、守りたい違反を1つ注入し、赤くなることを確かめてから採用する。
  **実行可能な検査へ昇格済み（change 16）。** `scripts/harness/*.test.ts` が各検査に違反を注入して赤くなることを見る。散文としてのこの項目は、検査を**新しく書くとき**の規則として残す（既存の検査は上のテストが守る）。

- **[L07] 環境依存の値は、自分の環境と符号や桁が違う値をテストに入れる**
  change 4 の cron が日境界を自前計算しており、UTC+9 では正しいまま Pacific/Auckland で1440分ずれた。テスト入力が全て `Asia/Tokyo` だったため、東京で動かす限り永久に出ない欠陥だった。
  タイムゾーン・ロケールのように環境で変わる入力は、自分の環境の値だけで固めない。
  change 16 で CI（Linux）を初めて動かしたら、**手元では出ない欠陥が4件**出た。`package-lock.json` に macOS 分のネイティブバイナリしか記録されておらず tsc も vitest も起動しない（npm/cli#4828）、cron worker の依存を CI が入れていない、biome が診断を20件で打ち切って注入したファイルを隠す、の4件である。**環境を1つしか動かしていない間は、その差は存在しないのと同じに見える。**

- **[L08] `- [x]` を付ける前に、そのタスク本文の検証条件を読み直す**
  change 4 のタスク1.2「同じ購読先を2回保存しても1件になることをテストで確認する」に完了印を付けたが、保存コードもテストも存在しなかった。レビューで指摘されるまで進捗は誤った数を示していた。
  タスクに書かれた検証条件を実際に満たしたときだけ完了にする。

- **[L09] 検査を走らせる前に、自分の変更が検査の入力に入っているか確かめる**
  change 5 で、履歴を走査する鍵の検査を**コミット前に**実行して「OK・終了コード 0」と報告した。走査対象は git の blob なので、直前に足した `.env.example` の行はまだ入っておらず、コミットした瞬間から常に赤になった。レビューで指摘されるまで気づかなかった。
  検査が何を入力にしているか（作業ツリーか、コミット済みの履歴か）を見て、必要なら先にコミットしてから走らせる。

- **[L10] 画面の確認は、人が押せる経路で辿る**
  change 6 で、タグの入力を `form.requestSubmit()` で送信して「付けられる」と確認した。実機では**決定ボタンが無く、確定する手段が存在しなかった**。プログラムからの送信は、押せないボタンや無い導線を素通りする。同時に、`id="tag-name"` が iOS に連絡先の名前欄だと推測され「連絡先を自動入力」が出ていたことも、実機でしか分からなかった。
  要素そのものを押す・打鍵と同じ経路で値を入れる。それができない環境なら、確認できていないことを明示して人に委ねる。

- **[L11] UI/UX の選択肢は、文ではなくモックで出す**
  change 11 の探索で「案C そのまま／案C + 高さ」の2案を文と図で並べて選ばせようとした。**動きの違いは文では判断できない**と指摘され、しかもこれは繰り返しの指摘だった（change 9 でも「UIのイメージがつかないから3案くらいモックを出して」と言われている）。
  見た目・動き・操作感に関する選択肢を出すときは、必ず**触れるモック**を作る。配色と文字は本物のトークンを使い、実機で開ける形（Artifact）で渡す。

- **[L12] 門を外したら、外したことを残す**
  change 16 の 9.2 で「CI が実際に赤くなること」を確かめるには、型エラーを含むコミットが要る。しかしコミット前の門は fail closed なので、それを通さない。`git commit` を含むコマンドは全て門を通るため plumbing でも迂回できず、`.claude/settings.json` を丸ごと外して作り、直後に戻した。**門を緩める**（例外を足す）のではなく**一度外して記録する**方を選んだ。緩めると、以後その穴は誰にも見えない。
  門・hook・検査を無効化したときは、何のために外したか・いつ戻したかを `.learnings` に残す。残っていない迂回は、次に同じ場面が来たときに「前もやったから」で通る。

- **[L13] 速くなった・効いたと言う前に、同一条件で複数回 A/B する**
  change 17 で、vitest の実行順序を変えたら注入テストが 5,623ms → 2,648ms に下がったので「効いた」と判断し、design に決定として書いた。CPU 負荷を固定して 6 回ずつ測り直したら、中央値の差は 290ms（1,658ms 対 1,371ms）でばらつきに埋もれた。**2 回の実行はマシンの負荷が違っており、設定の差ではなく負荷の差を測っていた。** 同じ測定で、両条件に約 938 秒の外れ値が 1 回ずつ出ている。1 回ずつの前後比較は、性能について何も言っていない。
  性能の改善を主張するときは、条件を固定して複数回取り、中央値と外れ値の両方を見る。差がばらつきに埋もれるなら**入れない**（効かないものを残すと、次に見た人が「これが効いている」と誤解する）。[L04] が「主張の前に測る」なら、これは「測っても比較条件が違えば意味がない」である。
