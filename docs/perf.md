# 速さの測り方と記録

初期表示を速くする change が続く（[nextjs-rework-plan.md](nextjs-rework-plan.md) の B 列）。
**同じ手順で誰が測っても同じ値になる**ようにするのがこの文書の目的である。

> L04「配色の性質を主張する前に実測する」と L13「速くなったと言う前に、同一条件で
> 複数回 A/B する」は、測らずに・条件を揃えずに「効いた」と言って覆った出来事を
> 2 度記録している。散文の規則で再発を防ぐのはやめ、**手順と検査**に移した。
> 検査は `npm run check:bundle`（転送量）。手順はこの文書（時間）。

要件そのもの（何秒以内か）は `openspec/specs/performance/spec.md` にある。
この文書は**測り方**を決め、**記録を積む**。

---

## 1. 指標は 3 つ

Lighthouse のスコアは使わない。1 つの数に混ぜると、何が変わったのか分からなくなる。

| 指標 | 定義 | 取り方 |
|---|---|---|
| **TTFB** | HTML の最初のバイトが届くまで | DevTools のネットワーク欄、または `performance_analyze_insight(insightName: "DocumentLatency")` |
| **一覧が読めるまで** | サインイン済みで `/` を開いてから、**一覧の最初のメモの本文が画面に描かれる**まで | Performance トレースで、その要素の描画時刻を読む（§4） |
| **タブ切替** | 下部のタブをタップしてから、切替先の中身が描かれるまで | Performance トレースで、タップのイベントから描画まで（§5） |

**「一覧が読めるまで」を LCP で代用しない。** LCP が一覧の要素であればその値を使ってよいが、
**毎回 LCP 要素が何かを確かめ、記録の備考に書く。** フォントの差し替えや骨格（skeleton）の
導入で LCP 要素は簡単に入れ替わる。入れ替わったことに気づかずに前後を比べると、
別の要素どうしを比べることになる。

転送量は指標ではなく**検査**にする。`npm run check:bundle`（§6）。

## 2. 条件を固定する

| 項目 | 値 |
|---|---|
| 対象 | 本番 `https://remoru.pokena191.workers.dev/`（サインイン済み） |
| 端末 A | 利用者の iPhone。**PWA としてホーム画面から起動**。Wi‑Fi |
| 端末 B | Mac の Chrome。iPhone のビューポート、ネットワーク「Fast 4G」、CPU 4 倍遅延 |
| 状態 | **ウォーム**を主とする。コールドは別の行 |
| データ | 利用者の実データ。**メモ数を記録に書く**（件数が変われば描画量が変わる） |
| 回数 | **5 回**。中央値と最大値の両方を残す |

**なぜ両方の端末で取るのか。** 実機は真の値だが、利用者にしか取れず、回線も端末の
状態も揃えられない。DevTools は再現性のある比較用で、絶対値は信用しない。
**change の採否は端末 B（DevTools）の中央値で判断し、実機は節目で確かめる。**
どちらの値を根拠にしたかを記録の備考に書く。

**ウォームとコールドの定義**

- **ウォーム** — 一度開いて閉じ、**続けて**もう一度開く。Workers が起きており、
  静的ファイルはキャッシュに乗っている。目標の 1 秒はこちらに適用する
- **コールド** — 10 分以上開いていない状態から開く。Workers の起動を含む。
  **記録はするが目標にしない**（起動時間はアプリ側で制御できない）

**5 回のうち 1 回でも他と桁が違う値が出たら、それは負荷の差である。**
捨てずに最大値として残し、備考に書く。L13 の測定では両条件に約 938 秒の外れ値が
1 回ずつ出ており、**平均だけを見ると両方とも壊れて見える**。中央値と最大値を並べる
のはそのためである。

## 3. サインイン済みで測る

`/` はサインインしていないと `/sign-in` に転送される（307）。curl では測れない。

1. E2E 用の Clerk テスト利用者でサインインする（資格情報は 1Password / Clerk の
   ダッシュボード。**このリポジトリは public なのでコミットしない**）
2. そのブラウザプロファイルを使い回す。Chrome DevTools MCP は既定で専用の
   プロファイルを持ち、セッションが残る
3. メモが 0 件だと「一覧の最初のメモの本文」が存在しない。**最低 5 件**入れておく

## 4. 端末 B（Chrome DevTools MCP）で測る

`web-perf` skill が使う `chrome-devtools` MCP サーバで行う。

```
claude mcp add chrome-devtools -- npx -y chrome-devtools-mcp@latest
```

### 手順

```
1. emulate_cpu(throttlingRate: 4)
2. emulate_network(throttlingOption: "Fast 4G")
3. navigate_page(url: "https://remoru.pokena191.workers.dev/")
   → サインイン済みで一覧が出ることを確かめる。/sign-in に飛んだら §3 に戻る
4. ウォームにする: もう一度 navigate_page して一覧が出るまで待つ
5. performance_start_trace(autoStop: true, reload: true)
6. 5 回繰り返す（4 と 5 を）
```

### トレースから何を読むか

| 読むもの | どこから |
|---|---|
| TTFB | `performance_analyze_insight(insightName: "DocumentLatency")` |
| LCP とその内訳・**LCP 要素** | `performance_analyze_insight(insightName: "LCPBreakdown")` |
| 描画を止めているもの | `performance_analyze_insight(insightName: "RenderBlocking")` |
| 何を何 KB 読んだか | `list_network_requests(resourceTypes: ["Script","Stylesheet","Document","Font"])` |

**LCP 要素が一覧の最初のメモの本文でないときは、LCP を「一覧が読めるまで」として
記録してはいけない。** そのときは `take_screenshot` を数百 ms 間隔で撮り、本文が
現れた最初のフレームの時刻を読む。**その判断を備考に書く。**

`insightName` は Chrome DevTools の版で変わる。通らないときは、トレースの応答に
並んでいる名前を見てから指定する。

### 残すもの

- 5 回ぶんの TTFB と「一覧が読めるまで」（中央値・最大値）
- LCP 要素が何だったか
- 一覧が描かれた瞬間のスクリーンショット 1 枚（`take_screenshot`）。
  **前後で見た目が違えば、速さだけを比べたことにならない**

## 5. タブ切替を測る

現状はクライアント状態の切替なので数十 ms のはずである。B2・B3 で経路を分けると
ネットワークが挟まる。**この値を悪化させないことが要件**なので、基準を先に取る。

```
1. §4 の 1〜4 でウォームにする
2. performance_start_trace(autoStop: false)
3. click(uid: <「復習」タブの uid>)   ← take_snapshot で uid を得る
4. 切替先の中身が出たら performance_stop_trace
5. メモ → 復習 → 記録 の順で 5 往復
```

**プログラムからの遷移（`router.push` の直接呼び出しなど）で測らない。**
L10 の出来事——`form.requestSubmit()` で「付けられる」と確認したが、実機には
決定ボタンが無かった——と同じ罠で、人が押せない経路は人の体験を測っていない。
`click` で**要素そのものを押す**。

## 6. 転送量は検査で見る（`npm run check:bundle`）

```
$ npm run check:bundle
/  実測 206.2 KB  予算 216.5 KB  差 -10.3 KB  (13 チャンク)
```

`scripts/harness/bundle-budget.mjs` が `.next` を読み、経路 1 つを開くために
読み込むクライアント JS を gzip して足し、`bundle-budget.json` の予算と比べる。
超えると非ゼロで終わり、チャンクごとの内訳を出す。`npm run check` に入っている
ので、**予算を超える変更はコミットできない**。

**読む場所は 2 か所の和集合である。**

- `.next/build-manifest.json` の `rootMainFiles` — 全経路共通の枠
- `.next/server/app/<経路>/page_client-reference-manifest.js` の
  `clientModules[].chunks` — その経路固有の Client Component

**この読み方は本番と突き合わせて確かめてある。** 2026-09-12、`/sign-in` の HTML が
挙げる 11 本を本番から実際に取得した合計が **223,559 B**、同じ式でローカルのビルドから
計算した値が **223,565 B**。差 6 バイト。読む場所が違えば、この一致は起きない。

### この検査が見ないもの

| 見ないもの | 大きさ | どこで見るか |
|---|---|---|
| `polyfillFiles` | 38.6 KB | 本番の `<script>` に `noModule` が付く。**現代のブラウザは読まない**ので予算に入れない |
| Clerk の `clerk.browser.js` | 81 KB | 別オリジンの CDN。ビルド成果物に現れない。§4 の `list_network_requests` で見る |
| `@clerk/ui` | 44 KB | 同上。B1 が減らす分はこの検査では捕まらない |
| Google Fonts の CSS | 87 KB | 同上。しかも**描画ブロック**する。§4 の `RenderBlocking` で見る |

**つまり `check:bundle` が緑でも、初期表示が速いとは限らない。** 検査は自前の
チャンクが太るのを止めるだけである。速くなったかどうかは §4 の時間で言う。

> `docs/nextjs-rework-plan.md` に「自前 JS 224 KB」とあるのは `/sign-in` の値で、
> しかも読まれない polyfill を含んでいる。`/` の値ではない。`/` は 206.2 KB。

### 予算を動かすとき

初期値は実測 + 5%。**下げるのは速くする change の仕事**で、各 change が自分の
成果分だけ下げる。上げるときは理由を change の design に残す。

## 7. 実機（端末 A）の手順 — 利用者に依頼する

**エージェントは実機を触れない。** ここは利用者にしか取れない。
値が届くまで、記録の実機の行は**空のまま**にし、「確認できていない」と明示する（L10）。

1. iPhone を Mac に Lightning / USB-C でつなぐ
2. iPhone: 設定 → Safari → 詳細 → **Web インスペクタ** をオンにする
3. iPhone: ホーム画面の Remoru を**長押しして一度終了**し、10 分以上待つ（コールド）か、
   一度開いて閉じてすぐ開く（ウォーム）
4. Mac: Safari → 開発 → <iPhone の名前> → Remoru を選ぶ
5. Safari のタイムラインを記録し、アプリを開く
6. 「一覧の最初のメモの本文が出た瞬間」のタイムラインの時刻を読む
7. ウォーム 5 回、コールド 3 回。**メモの件数**も控える

読み取りが難しければ、**画面収録（設定 → コントロールセンター → 画面収録）で
アプリを開く様子を撮って渡してもらう**だけでもよい。60 fps なので、
アイコンを押したフレームと本文が出たフレームの差から 16 ms 刻みで出せる。

## 8. 記録

**1 change につき「前」「後」の 2 行。** 前の行は、前の change の後の行と
同じでなければならない。違えば change 以外の何かが変わっているので、備考に書く。

単位は ms。`中央値 / 最大値` の形で書く。取れていない値は空欄にし、
**「測っていない」と「0」を混ぜない**。

| 日付 | change | 条件 | TTFB | 一覧が読めるまで | タブ切替 | JS gzip | メモ数 | 備考 |
|---|---|---|---|---|---|---|---|---|
| 2026-09-12 | measure-first-paint（基準） | 端末B ウォーム | | | | 206.2 KB | | `/` の自前チャンク 13 本。時間は未計測 |
| 2026-09-12 | measure-first-paint（基準） | 端末B コールド | | | | 206.2 KB | | |
| 2026-09-12 | measure-first-paint（基準） | 端末A 実機 ウォーム | | | | — | | **未計測。利用者に依頼中**（§7） |

**参考値**（2026-09-12、curl 3 回、サインイン**していない**経路）

| 対象 | 値 |
|---|---|
| `/` 未サインイン（307）TTFB | 0.53 / 0.53 / 0.99 秒 |
| `/sign-in` TTFB | 0.07 / 0.48 / 0.53 秒（ばらつきが大きい。コールドスタートの疑い） |
| `/sign-in` の自前 JS 11 本（本番から実取得、polyfill 込み） | 223,559 B |

## 9. 実利用者の値（Cloudflare Web Analytics）

本番に出したあとの実利用者の Core Web Vitals は Cloudflare Web Analytics で見る。
Cookie を使わず無料で、ビーコン 1 本をルート layout に置くだけで集まる。

**これは検査の代わりではない。** 利用者が 1 人で回数が少なく、ばらつきが読めない。
change の前後比較には**使わない**。事後に「実際の利用者は何秒で見えているか」を
知るためのものである。
