## 1. サインインしていないアカウントの通知が端末に届く

**2026-08-29 に調査。データだけ直し、根本対処は先送り。**

### 何が起きたか

利用者の iPhone に、サインインしていないアカウントの通知が毎日届いていた。
通知の本文はそのメモから作った問いなので、**別アカウントの中身が表示されて
いた**。煩わしさではなく、**利用者どうしの分離が破れている**。

本番の `push_subscriptions` は3件で、うち1件は 8/24 にテスト用アカウントで
購読したもの（`web.push.apple.com/QGJxQRly…`）。同じ端末の 8/30 の購読は
**別の送信先**（`…/QF7saUpoyu…`）だった。

その場の対処として、テスト用アカウントの購読・メモ・通知設定を消した。
**この対処は今ある被害を止めただけで、再発は防いでいない。**

### 根本原因（検証済み）

送信先（`endpoint`）はブラウザに属するが、行は購読した瞬間の利用者を
焼き付けたまま残る。消える契機は2つしかない。

```
① その利用者が自分で通知をオフにする
② 配信側が 404/410 を返す

サインアウト   → 何も起きない
アカウント切替 → 何も起きない
期限切れ       → 何も起きない
```

`saveSubscription`（`lib/notification-subscriptions.ts`）は衝突時に持ち主を
移すが、**同じ送信先が返ってきたときしか働かない**。

### 検証済みの事実

| | 事実 | 根拠 |
|---|---|---|
| セッションの寿命 | **7日で必ず切れる**（`maximum_lifetime` 604800秒、`inactivity_timeout` 無効） | `clerk config pull` |
| 明示のサインアウトより期限切れが多い | 上の帰結 | ― |
| cron はその利用者の購読を**全部**引く | `WHERE user_id = ?1` | `cron-worker/src/index.ts:56` |
| 設定の意思は**利用者ごと** | `notification_settings.enabled` | `db/schema.ts` |
| 購読は**端末ごと**（`endpoint` が一意） | 端末が主・利用者は属性 | `db/schema.ts:97` |
| 設定の行が無い利用者は選ばれない | cron が `notification_settings` を全件読む | `index.ts:74` |
| 通知は `tag` で1つに畳まれる | `tag: "remoru-review"`, `renotify: false` | `public/sw.js:33` |
| cron は毎時0分、既定は21時 | 全利用者が同じ実行に乗る | `cron-worker/wrangler.jsonc:15` |

### 却下した案と、その理由

**「サインアウトで消す」だけでは足りない。** 7日の期限切れを塞げない。
利用者が端末から離れる主な経路は明示のサインアウトではない。

**「サインインで持ち主を移す」（Pushpad / OneSignal の作法）は、そのまま
移植すると新しい漏れを作る。**

```
A の iPad で B がサインイン → iPad が B のものになる
B が自分の携帯で通知をオン（enabled は利用者ごと）
→ cron は B の購読を全部引く → A の iPad にも B の問いが届く
```

あちらの製品で移譲が正しいのは**意思が端末レコード側にある**ため。Remoru は
意思が利用者側にあるので、粒度が違う。**移譲ではなく削除**が正しい形。

**どちらの案も、今回の孤児には届かない可能性が高い。** `subscribeToPush` は
`getSubscription()` の既存を再利用する（`app/push-subscribe.ts:68`）ので、
端末が 8/24 の購読を持ったままなら 8/30 に同じ送信先が送られ、移譲が働いて
1行になっていたはず。2行あるということは 8/30 時点で `getSubscription()` が
null を返した ＝ **その送信先は端末から二度と出てこない**。

navigator.serviceWorker.getRegistration()

`QGJxQRly…`（8/24）が返れば起動時の突き合わせで足りる。

### 直すなら層で積む

| 層 | 何をするか | 塞ぐもの |
|---|---|---|
| 1 | 起動のたびの突き合わせ。他人の行は**削除**。`enabled` かつ許可済みで購読が無ければ作り直す | 切替・期限切れ |
| 2 | サインアウト時の解除 | 立ち去った瞬間からの窓 |
| 3 | **鮮度による始末**（一定期間その端末から名乗り出が無ければ送らない／消す） | **孤児。他のどの層も塞げない** |
| 4 | 送信の中身を伏せる（払い出し先の利用者と、端末がいま知っている利用者が食い違うとき） | すり抜けた分の中身の漏れ |

**孤児を消せる仕組みは時間しかない。**

### 層2を実装したときに見つけた欠陥（同じ轍を踏まないために）

端末側の購読を解除しながら `notification_settings` に触れないと、
**サインアウト → 再サインインで通知が静かに死ぬ**。`enabled` は true のまま
購読が無いので cron は `subs.length === 0` で飛ばし、設定画面は
`payload.settings.enabled` だけを見て「毎日21時ごろ」と**嘘をつく**
（`app/notification-settings.tsx:125`）。

突き合わせは「奪う」ではなく「**この端末の状態を、いまの利用者の意思に
合わせる**」でなければならない。

### spec の書き方（いまの書き方は不正確）

「購読は利用者と端末の組に属する」は誤り。`endpoint` が一意なので端末が主。
組に属するなら1端末に2行あり得て、移譲が説明できない。

```
送信先は端末を指す。1つの送信先には、ちょうど1人の持ち主がいる SHALL。

ある送信先へ送る通知は、その端末でいま（またはごく最近）その利用者が
サインインしている場合に限 SHALL る。

「この端末で通知を受け取る」意思は、利用者と端末の組ごとに持 SHALL つ。
ある利用者が別の端末で通知を有効にしたことが、この端末を配信先にしては
MUST NOT ならない。   ← 今回破れたのはこの性質
```

### 付随して見つかった小さな欠陥

- `unsubscribeFromPush` 相当の処理が DELETE の応答を見ずに端末側を解除する。
  行が他人のものだと消えないのに端末側だけ解除され、**行を消す手がかりを
  自ら捨てる**
- `saveSubscription` の移譲後も `createdAt` は元の値のまま。鮮度による掃除
  （層3）を作るなら `lastSeenAt` を別に持つ必要がある
- cron の期限切れ削除（`index.ts:133`）は `WHERE id = ?1` だけで持ち主を
  見ない。**cron 内のこの1文だけが持ち主照合の規則の外**にある
- `subscribeToPush` は既存の購読を再利用するとき、その `applicationServerKey`
  が現在の VAPID 公開鍵と一致するか見ていない。鍵を回すと消せない購読が残る
